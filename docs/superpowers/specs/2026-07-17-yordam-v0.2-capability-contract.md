# Yordam v0.2 Capability Contract

Status: approved normative design
Date: 2026-07-17
Parent PRD: [Yordam v0.2 Trusted Extensibility](2026-07-17-yordam-v0.2-prd.md)

## 1. Capability

After v0.2 ships, a solo developer can give Yordam a task with explicit completion criteria, let one agent execute it through built-in and configured extension surfaces, inspect each consequential activity through linked evidence and authorization, recover through immutable session forks, and receive a receipt that distinguishes verified outcomes from unknown effects.

This contract defines what must remain true across the Foundation, Trust Loop, Extensibility, Security, and Acceptance specifications. Where a lower-level spec conflicts with this document, this contract wins unless it is explicitly amended and re-approved.

## 2. Policy Classification

This document distinguishes three decision classes:

- **Fixed product policy:** user-visible promise that implementation cannot weaken.
- **Architecture constraint:** implementation boundary required to preserve policy and recovery.
- **Deferred capability:** explicitly outside v0.2 and not an implementation gap.

## 3. Fixed Product Policies

### 3.1 Task and Outcome

1. A task has a stable task identity, goal, and versioned outcome contract.
2. The user may supply completion criteria. When criteria are missing, the agent may propose observable criteria.
3. Goal and draft contract become durable before contract drafting begins. Contract drafting may use a provider and policy-authorized observation-only discovery, but mutation-capable tools are absent from that phase.
4. The active contract must contain at least one required criterion and be visible and frozen before any mutation-capable provider phase or mutation.
5. An agent cannot silently remove, weaken, or mark required criteria optional.
6. Contract changes require an explicit amendment event and visible provenance.
7. `turn.completed` and `outcome.verified` are distinct states.
8. `verified` requires evidence-backed verification for every required criterion. A waiver produces `completed_with_waivers`, never `verified`.
9. Assistant text alone cannot satisfy a verification requirement.
10. A terminal `partial`, `failed`, `unknown`, or `completed_with_waivers` task may be explicitly reopened for a new turn without rewriting its prior assessment.

### 3.2 Activity and Evidence

Every consequential operation exposes four separate projections:

- **Purpose:** a concise actor-authored explanation of the intended task or control-operation contribution. It is required in the durable plan and is a claim, not evidence.
- **Evidence:** system-observed inputs, canonical scopes, diffs, outputs, hashes, timing, usage, and artifacts.
- **Decision:** effective policy, actor, exact scope, reason, risk, and grant lifetime.
- **Verification:** observed postconditions, receipts, coverage limits, and unknown effects.

Yordam must not expose or persist raw chain-of-thought, hidden scratchpads, or private reasoning streams. Provider reasoning summaries may be shown only when they are an explicit provider feature, safe to expose, and labeled as a summary rather than evidence.

A consequential operation is any operation that can disclose non-public data, incur cost, mutate local or remote state, start a process, use a credential, change model-visible behavior, or make a verification claim. This includes provider requests, MCP and OAuth network activity, stdio MCP startup, tools, executable verifiers, command hooks, restore, and project-source activation. Pure parsing, schema validation, digest calculation over already authorized local data, and projection rebuilds are not consequential.

### 3.3 Authorization

1. Authentication to a provider or MCP server does not authorize a requested action.
2. Every consequential operation is evaluated using Yordam's authorization model, including provider egress, MCP lifecycle and items, executable verifiers, hooks, and restore.
3. Permission scopes are structured and canonical, not only human-readable strings.
4. A durable allow decision must exist before the corresponding side effect begins. A once-decision is atomically consumed by the matching `activity.started` commit.
5. A scope change during pre-execution re-resolution invalidates the earlier decision.
6. Low-risk in-workspace observation may be policy-allowed without a modal.
7. A session grant must state the future capability it grants, not imply it approves only the current arguments.
8. Broad trusted-shell acknowledgement is separate from exact-command permission, remains visible, and is revocable.
9. Policy resolution is monotonic: platform impossibility and hard deny are terminal; project policy intersects and may only narrow the user capability set; grants and interactive responses resolve only an effective `ask` within all remaining constraints. No later layer can override a deny.
10. In headless mode, unresolved `ask` fails closed without starting the action.
11. Every decision binds principal, session or control operation, task when present, turn when present, activity, call or queue identity, canonical source, action, resources, plan digest, runtime generation, policy generation, decision nonce, lifetime, and expiry.

### 3.4 Checkpoint, Rewind, and Restore

1. A checkpoint is a durable history anchor with explicit coverage metadata; it is not automatically a full filesystem snapshot.
2. Automatic checkpoints are created before consequential mutations.
3. Rewind creates and activates a new session fork at a selected checkpoint.
4. Rewind never truncates, rewrites, or deletes the source session journal.
5. A context-only fork leaves the workspace unchanged.
6. Exact workspace restore is available only for built-in edit operations whose complete restore material was durably captured before mutation.
7. Restore revalidates current preimages and stops on drift before overwriting any changed file.
8. Shell, command-hook, local-MCP arbitrary process, network, and remote-MCP effects are never claimed as restored merely because a checkpoint exists.
9. Forks do not inherit session grants, broad trusted-shell acknowledgement, pending approvals, or transient MCP authorization state.
10. A child fork anchors an immutable parent prefix and begins with child-local bootstrap events that terminalize inherited in-progress work as historical interruption and establish an idle child state. No inherited plan is actionable.

### 3.5 Provider Behavior

1. OpenAI, Anthropic, and Gemini have native adapters. OpenAI-compatible endpoints retain a separate adapter.
2. Provider-neutral messages use structured content blocks rather than forcing every native feature into Chat Completions text.
3. Model descriptors expose known context windows, capability state (`supported`, `unsupported`, or `unknown`), usage support, and pricing provenance.
4. A required unsupported capability produces a visible `capability_unavailable` failure.
5. Yordam does not silently emulate a required capability in a way that changes semantics.
6. Usage is labeled `provider_reported`, `estimated`, or `unknown`. Cost is labeled `calculated`, `actual_billed`, or `unknown`; `actual_billed` requires provider billing evidence rather than local price multiplication.

### 3.6 MCP Behavior

1. v0.2 supports tools, resources, and prompts.
2. v0.2 supports local stdio and remote Streamable HTTP transports.
3. MCP protocol version and capabilities are negotiated before any server item becomes model-visible.
4. Tool annotations and server instructions are always untrusted content for authorization. Trust permits connection or use; it never turns annotations into policy authority.
5. MCP canonical identities include logical server and item identities, source revision, and descriptor or schema digest. Provider-visible tool names are aliases, not authorization keys.
6. Remote bearer credentials are secret references, never literal config fields.
7. Remote OAuth follows the pinned MCP authorization-profile revision recorded by the release: protected-resource discovery, authorization-server discovery, PKCE S256, state validation, resource indicators, local issuance binding, and bounded step-up authorization.
8. OAuth tokens are stored in the OS credential store. When no supported store is available, tokens remain process-only; there is no plaintext fallback.
9. Stdio credentials are provided only through an explicit environment allowlist.

### 3.7 Project Trust and Extensions

1. Project agents, instructions, skills, hooks, and MCP definitions may be discovered before trust but cannot be activated or inserted into model context before explicit workspace trust.
2. Workspace trust is bound to the canonical workspace and trusted configuration provenance.
3. A changed executable launch manifest, local MCP launch definition, remote MCP endpoint or transport identity, credential reference, or broader policy capability invalidates the relevant trust and requires re-approval.
4. Text-only instruction or skill changes may activate under existing workspace trust but must expose source path, digest, and runtime generation in the ledger.
5. Command hooks use the same execution, authorization, timeout, redaction, and evidence boundaries as other process actions.
6. Hook phases and failure policies are typed; hooks cannot recursively trigger themselves without a bounded recursion guard.
7. Executable launch trust binds a canonical semantic manifest: resolved executable or script bytes, interpreter, arguments, working directory, environment names, credential bindings, source revision, and declared dependency locks. The launch adapter hashes source bytes through race-resistant open handles, then executes verified descriptors where supported or verified private immutable staging copies. It never spawns from the re-resolvable repository path.
8. Trust revocation is a live deny overlay checked before every dispatch, including active turns. New project-owned actions stop immediately; running project processes are terminated where possible and otherwise become uncertain.

### 3.8 Execution Profiles

v0.2 exposes two policy profiles:

- `restricted local`: policy defaults deny or ask for process, network, boundary-crossing, and mutation capabilities.
- `trusted local`: the user permits broader execution with explicit warnings and durable acknowledgement.

Neither profile is an operating-system sandbox. The UI, documentation, headless stream, and receipts must use language that distinguishes policy restriction from enforced process confinement.

### 3.9 Headless and Metrics

1. Headless mode emits a versioned JSONL event stream and, on orderly termination while stdout and storage remain writable, one final `RunReceipt`.
2. Headless correlation is a discriminated union. Every event identifies journal kind/ID, timestamp, schema version, and durability. Workspace-control events require `control_operation_id` and may carry optional task/turn/activity causation IDs; session events require `session_id`; task, turn, and activity IDs are required only when applicable.
3. Headless mode has deterministic exit categories for verified success, completed with waivers, partial, unknown, permission required, configuration failure, capability failure, authentication required, execution or verification failure, cancellation, and storage corruption.
4. v0.2 has no bidirectional headless approval channel and no session-attach protocol.
5. Product metrics are computed locally from the ledger.
6. No automatic telemetry is sent. Metric export requires an explicit user action.

## 4. Architecture Constraints

### 4.1 Single Active Turn

Yordam remains one process with one active turn per application instance. Model tool calls and consequential effects execute sequentially. Parallel tool execution and subagents are deferred capabilities.

Taskless lifecycle, reload, credential, MCP connection, and recovery work uses a durable `ControlOperation` identity and the same single serialized consequential-effect lane. Runtime-generation preparation is pure until a separately authorized control operation performs network or process activity. No background consequential operation runs concurrently with an active turn.

### 4.2 Durable Ordering

For contract drafting, goal and draft contract become durable before an authorized provider request. Observation-only discovery results become durable before they are returned to the drafting provider. The frozen contract is mandatory before mutation-capable tools are advertised.

For each consequential action, the following order is mandatory:

1. canonical action plan, purpose, resource scope, and plan digest become durable;
2. when mutation coverage is required, checkpoint and confidential restore material referencing that plan digest become durable;
3. final pre-execution validation confirms the same plan digest and resources;
4. effective authorization becomes durable;
5. the once-decision is atomically consumed with `activity.started`;
6. side effect may begin;
7. terminal result and evidence become durable;
8. result may be returned to the provider;
9. criterion assessment and receipts become durable.

Any action-plan or resource change after checkpointing invalidates both checkpoint coverage and authorization and returns to planning.

If storage cannot preserve this order, the active turn stops before additional provider or effect activity.

### 4.3 Runtime Generation

Every turn captures one immutable semantic runtime-generation manifest containing provider and model descriptors, tool and MCP catalog revisions, instructions, skills, hooks, policy generation, execution-profile configuration, and limits. Mutable transport and credential leases are separate and may refresh only when their immutable server identity, resource, issuer, client, scopes, source revision, and policy constraints remain unchanged.

Configuration reload may prepare and activate a new generation for future turns. It cannot mutate the generation used by an active turn.

A live hard-deny and revocation epoch is checked before every dispatch and may block a new action in an active turn without mutating that turn's semantic generation.

### 4.4 Versioned Protocols

The event journal and application-facing command/snapshot/event stream are versioned independently from internal Go structs. TUI and headless mode consume the same application protocol projections.

Durable history has two journal domains:

- a workspace control journal owns runtime-generation activation, workspace trust, MCP lifecycle, credential status, and taskless `ControlOperation` events;
- a session journal owns task, turn, activity, decision, checkpoint, evidence-link, and outcome history.

Every envelope identifies journal kind and journal ID. Session ID is required only for session-journal events. Application snapshots and subscriptions use an `ApplicationCursor`: a vector containing the exact workspace-control committed cursor, the selected session committed cursor when any, and a live stream epoch/sequence for transient ordering. Durable catch-up reads strictly after each vector component and deterministically merges by event time then event ID; transient events are live-only and never claimed resumable across process epochs.

### 4.5 Typed Event Payloads

Every known event kind and payload version has a validator and canonical decoder. Unknown event kinds or unsupported payload versions are preserved for inspection but make the session non-writable unless the envelope declares a projection-domain compatibility marker that the reader explicitly understands as safely skippable. Invalid known payloads are corruption, not ignored data.

### 4.6 Session Lineage

A fork references an immutable parent prefix through parent session, committed parent cursor, and checkpoint digest. Child-local sequence identity remains distinct. An atomic child bootstrap batch records lineage, trust-state reset, inherited historical interruptions, and idle child state. Projection composes ancestry and child events without copying or mutating parent history.

A lineage cursor is structured as view session, origin session, and origin committed cursor. It never flattens parent and child local sequences into one ambiguous number. Missing parents, ancestry cycles, and lineage depth beyond 64 open the child read-only.

### 4.7 Evidence Ownership

Display and verification evidence metadata belongs to activities and subjects. Its blob storage is content-addressed so forks can reference identical immutable evidence without path-coupling to the parent session.

Exact restore bytes use a separate confidential recovery-material store. Recovery material is never model-visible, renderable, exported as ordinary evidence, or automatically included in metrics. It is stored with restrictive permissions and platform-backed encryption when available. When secure retention cannot be provided or registered secret bytes are detected, exact restore is unavailable for that subject; digest-only drift detection may remain.

### 4.8 Authorization Inputs

Authorization requests include:

- principal and actor;
- session, task, turn, and activity identity;
- canonical tool or hook identity and source;
- requested action and structured resource targets;
- local or remote execution locus;
- requested and effective execution profile;
- effect class, boundary, reversibility, and verification coverage;
- policy provenance.

Authorization decisions repeat all binding identities, add policy generation, decision nonce, lifetime, expiry, and the committed plan digest. A once-decision and activity start are committed atomically so concurrent or repeated consumers cannot reuse it.

### 4.9 Application Projection

The canonical application snapshot contains durable state at a known journal head plus ephemeral runtime status. It includes task, outcome, lineage, active activity, provider capability, MCP state, instruction provenance, permissions, context budget, usage, cost, checkpoints, evidence, receipts, and recovery diagnostics.

## 5. Actors and Surfaces

| Actor | Responsibility | Surfaces |
|---|---|---|
| User | Defines goals, approves contracts and risks, selects recovery actions | TUI, CLI, local config |
| Agent | Proposes plans, criteria, purposes, tool calls, and final explanations | Provider request/response contract |
| Turn orchestrator | Enforces lifecycle, sequential execution, and durable ordering | Internal application service |
| Authorization engine | Resolves policy and interactive decision requirements | Permission cards, headless failures, ledger |
| Verifier | Produces bounded claims backed by evidence | Receipts and criterion assessments |
| Provider adapter | Translates native model behavior and usage | Provider catalog and event stream |
| MCP server | Supplies tools, resources, and prompts | MCP client connection and catalog |
| Hook | Observes, vetoes, annotates, or requires lifecycle behavior | Typed hook phases and receipts |
| TUI | Renders application snapshots and sends commands | Interactive operator cockpit |
| Headless client | Reads JSONL and process exit status | One-way automation interface |

## 6. Required States and Transitions

### 6.1 Task

```text
draft -> contract_drafting -> contract_proposed -> contract_frozen -> running
      -> verifying -> verified | completed_with_waivers | partial | failed | unknown | cancelled
partial | failed | unknown | completed_with_waivers -> reopened -> running
```

### 6.2 Turn

```text
accepted -> contract_drafting -> planning_context -> waiting_provider -> receiving_provider
         -> planning_action -> awaiting_permission -> executing
         -> recording_evidence -> verifying -> completed
         -> failed | interrupted
```

`contract_drafting` contains its own drafting-provider and observation-only discovery sub-activities before contract freeze. `awaiting_permission` may be skipped when policy resolves the action. `executing` remains sequential.

### 6.3 Activity

```text
planned -> denied | cancelled | authorized
authorized -> cancelled | started
started -> succeeded | failed | interrupted_no_effect | uncertain
```

An activity cannot transition from `planned` to `started` without a durable authorization when the activity is consequential.

### 6.4 MCP Connection

```text
configured -> authenticating -> initializing -> ready
           -> auth_required | incompatible | disconnected | failed
```

Items become catalog-visible only in `ready` after successful protocol and capability negotiation.

### 6.5 Checkpoint and Restore

```text
checkpoint_preparing -> checkpoint_ready | checkpoint_failed
fork_preparing -> fork_ready | fork_failed
restore_planned -> denied | cancelled | awaiting_permission
awaiting_permission -> denied | cancelled | restore_not_applied | authorized
authorized -> restore_not_applied | restoring
restoring -> restored | recovery_required
```

Only `checkpoint_ready` checkpoints may be selected for rewind.

## 7. Core Invariants

1. Event sequence and causation are deterministic within each workspace-control or session-local journal.
2. Side effects never precede required durable intent and authorization.
3. Provider results never observe a tool terminal result before that result is durable.
4. Recovery never automatically re-executes an unmatched consequential activity.
5. A source session and the parent prefix anchored by a fork remain unchanged after fork or rewind.
6. Fork projection cannot inherit security-sensitive session state unless this contract explicitly permits it.
7. A receipt never claims broader verification than its evidence and execution environment support.
8. Unknown usage, cost, restore coverage, or remote state remains explicitly unknown.
9. Project and MCP metadata cannot silently broaden user authorization.
10. Registered secret byte sequences never enter durable event payloads, ordinary evidence blobs, user-facing errors, or model-visible tool results. Confidential recovery material is the sole raw-byte exception and follows Section 4.7. Transformed, unknown, or independently read secrets emitted by an unsandboxed process cannot be guaranteed detectable; the child-environment allowlist minimizes that exposure.

## 8. Data Ownership

| Data | Owner | Durable Form |
|---|---|---|
| Workspace control operations and runtime activation | Workspace control journal | Versioned append-only control events and rebuildable cache |
| Session lineage and event history | Session repository | Versioned append-only journal and metadata cache |
| Task and outcome contract | Task projection from journal | Versioned outcome events |
| Activities and decisions | Activity ledger projection | Versioned lifecycle events |
| Display evidence and receipts | Evidence store | Metadata plus content-addressed redacted blobs |
| Exact restore bytes | Confidential recovery store | Access-restricted material, encrypted when available, never model-visible or normally exportable |
| Provider/model capabilities | Runtime generation | Config plus negotiated descriptors; selected facts recorded per turn |
| MCP connection state | Runtime generation | Durable configuration and bounded lifecycle events; no raw tokens |
| OAuth tokens | Credential manager | OS credential store or process memory |
| User/project definitions | Configuration resolver | Source path, scope, digest, trust status, runtime generation |
| Product metrics | Local metric projection | Derived local report; no automatic network export |

Metadata files and indexes are rebuildable caches. The journal and evidence blobs are the durable sources of truth.

## 9. Failure and Recovery Contract

- A storage failure stops further provider and side-effect activity.
- An unsupported event envelope or invalid known payload opens the validated prefix read-only.
- An incomplete final write is preserved as a recovery artifact and excluded from projection.
- An unmatched started activity is terminalized as `interrupted_no_effect` or `uncertain` without automatic re-execution.
- A provider stream that emitted content is not automatically retried as a fresh attempt.
- A mutation-capable remote request is never automatically resent after request bytes may have reached the server. Reconnection may resume the existing response stream only. Any retry is a new explicitly planned and authorized activity, while the original remains uncertain.
- MCP protocol incompatibility prevents catalog exposure.
- OAuth step-up attempts are bounded and cannot loop indefinitely.
- A changed restore preimage produces `drifted` before any restore write.
- A partial restore records every confirmed and uncertain path and does not retry automatically.
- Restore creates and activates a blocked child fork before workspace writes. Any post-write failure leaves that child in `recovery_required`; normal task execution remains blocked until reconciliation is recorded.
- A command process whose termination cannot be confirmed yields an uncertain cleanup state.

## 10. Deferred Capabilities

The following are intentionally deferred and must not be treated as missing v0.2 implementation:

- subagents, parallel work, and agent dependency graphs;
- bidirectional headless control and session attach;
- remote runners or daemon/client architecture;
- OS-enforced sandbox backends;
- universal workspace snapshots;
- automatic reversal of external effects;
- extension marketplaces and package management;
- team, organization, fleet, or cloud control planes.
