# Yordam v0.3–v1.0 Roadmap Design

Status: superseded on 2026-07-19; retained as historical context only
Superseded by: [Yordam v0.3 Self-Hosted Agent Runtime Design](2026-07-19-yordam-v0.3-self-hosted-agent-runtime-design.md)
Date: 2026-07-17
Historical prerequisite: Yordam v0.2 Trusted Extensibility is released and its acceptance gates pass
Primary persona: solo, local-first power-user developer
Primary interface: terminal UI
Secondary interfaces by v1.0: headless CLI, local protocol, SDK, and ACP clients
Delivery policy: scope and quality are fixed; schedule is flexible

> This roadmap is no longer an implementation source. In particular, its
> `v0.3 Verified Delegation` scope and the related uncommitted implementation
> plan were replaced by the approved self-hosted-development scope linked above.
> Later-release sections remain historical ideas and carry no delivery commitment.

## 1. Decision Summary

Yordam will follow a trust-first autonomy strategy from v0.3 through v1.0.
It will use OpenCode as the reference for broad coding-agent platform capabilities
and MiMo-Code as the reference for memory, orchestration, workflows, and autonomous
operation. It will not become a Go rewrite of either product. Each adopted capability
must enter Yordam through the authorization, evidence, recovery, and verification
contracts established in v0.2.

The product position is:

> Yordam is the local coding-agent platform that can exercise substantial autonomy
> while making consequential work permissioned, evidence-linked, recoverable where
> technically possible, and independently verifiable.

The strategic tension is **autonomy × trustworthiness**. Yordam succeeds only when it
raises both axes together. Capability breadth without reliable control is not success,
and perfect inspectability without useful autonomy is not success.

## 2. Approved Product Boundaries

The following decisions are fixed for this roadmap:

1. Yordam remains a Go application. OpenCode and MiMo-Code behavior may be studied,
   tested, and ported, but their TypeScript/Bun runtimes are not embedded into the core.
2. Solo, local-first power users remain the primary audience through v1.0.
3. The TUI remains the default interactive client.
4. Server, SDK, and Agent Client Protocol support are secondary client surfaces built
   after the agent core reaches competitive coding intelligence.
5. Desktop applications, team administration, shared RBAC, and fleet management are
   post-v1 product areas.
6. Direct third-party code reuse must be small, isolated, license-compatible, attributed,
   and covered by Yordam-owned tests. Behavioral reimplementation is the default.
7. Claims that Yordam matches or exceeds another agent require a pinned, reproducible
   benchmark rather than a feature checklist or subjective demo.

## 3. Competitive Reference Frame

### 3.1 OpenCode: Platform Baseline

OpenCode is the reference for:

- broad model-provider and local-model support;
- built-in coding tools, LSP integration, formatters, and patch workflows;
- primary agents, subagents, child sessions, and session navigation;
- MCP, custom tools, skills, and JavaScript/TypeScript plugins;
- server, OpenAPI, SDK, ACP, web, IDE, and desktop client surfaces;
- session forking, revert flows, and shareable sessions.

Primary sources:

- <https://github.com/anomalyco/opencode>
- <https://opencode.ai/docs/providers/>
- <https://opencode.ai/docs/agents/>
- <https://opencode.ai/docs/tools/>
- <https://opencode.ai/docs/plugins/>
- <https://opencode.ai/docs/server/>
- <https://opencode.ai/docs/acp/>

### 3.2 MiMo-Code: Autonomy Baseline

MiMo-Code is the reference for:

- project memory, session checkpoints, scratch notes, and task progress;
- context reconstruction and budgeted memory injection;
- tree-shaped task tracking and parallel subagents;
- goal-based stop conditions with an independent judge;
- deterministic, resumable, multi-agent workflows;
- best-of-N model execution and judge selection;
- mining sessions for reusable memory, skills, commands, and workflows.

Primary source:

- <https://github.com/XiaomiMiMo/MiMo-Code>

### 3.3 Yordam: Differentiation Baseline

Yordam v0.2 contributes the contracts that every later capability must preserve:

- goal and versioned outcome contract;
- explicit separation of Purpose, Evidence, Decision, and Verification;
- durable authorization before side effects;
- evidence-linked activity ledger;
- structured risk and permission scopes;
- immutable session forks and honest restore coverage;
- verification receipts and explicit unknown effects;
- provider capability negotiation and trusted extensibility.

The v0.2 capability contract remains normative unless a later specification explicitly
amends it without weakening its user-visible trust promises.

## 4. Adoption Policy

### 4.1 What Yordam Adopts

Yordam may adopt:

- documented user flows and interaction concepts;
- open protocols such as MCP and ACP;
- provider-neutral schemas and interoperability patterns;
- task, memory, workflow, and session concepts;
- benchmark scenarios and externally observable behavior;
- small license-compatible utilities when reimplementation adds no product value.

### 4.2 What Yordam Does Not Adopt

Yordam does not adopt:

- permissive-by-default execution;
- automatically installed executable plugins without trust review;
- memory or extension content as authorization authority;
- hidden self-modification;
- uncontrolled parallel mutation of a shared workspace;
- model-authored completion claims as verification;
- a second general-purpose application runtime inside the core merely for compatibility;
- credentials stored as literal project or global configuration values.

### 4.3 Capability Admission Contract

Every post-v0.2 capability must define:

1. canonical identity and provenance;
2. user-visible purpose;
3. authorization and trust boundary;
4. durable lifecycle and crash behavior;
5. evidence produced and retained;
6. reversibility and recovery coverage;
7. resource, token, time, and cost budgets;
8. verification method and unknown-effect classification;
9. compatibility and migration behavior;
10. a benchmark or acceptance scenario.

## 5. Roadmap Overview

```text
v0.2 Trusted Extensibility
  -> v0.3 Verified Delegation
  -> v0.4 Provenance Memory
  -> v0.5 Deterministic Workflows
  -> v0.6 Code Intelligence
  -> v0.7 Local Agent Protocol
  -> v0.8 Enforced Execution
  -> v0.9 Trusted Ecosystem and Evolution
  -> v1.0 Verified Agent Platform
```

Each release has one primary product thesis. A release may prepare internal seams for a
later capability, but it must not silently pull the later release's user-visible scope
forward. Each release retains all prior acceptance suites.

## 6. v0.3 — Verified Delegation

### 6.1 Capability

A user can delegate a large task to multiple specialized workers while retaining a
single outcome contract, bounded authority, visible progress, deterministic ownership,
and evidence-linked integration.

### 6.2 Required Surfaces

- parent task and child task identities;
- task dependency graph with explicit readiness state;
- primary, worker, reviewer, and judge roles;
- per-worker provider/model, tool, token, cost, time, and concurrency budgets;
- worker lifecycle, cancellation, retry, and terminal receipts;
- isolated git worktree or disposable workspace ownership for mutation workers;
- parent/child session navigation in the TUI;
- merge planning, conflict handling, review, and merge verification.

### 6.3 Core Invariants

1. The parent outcome contract remains authoritative for the task.
2. A child cannot grant itself permissions or broaden parent policy.
3. Child capability is an explicit lease bounded by actor, task, resources, runtime
   generation, expiry, and budget.
4. Parallel observation may share an immutable repository snapshot.
5. Parallel mutation never targets the same writable workspace by default.
6. A worker result is evidence-bearing input, not an automatically accepted conclusion.
7. Merge is a separately planned, authorized, and verified activity.
8. Worker failure, cancellation, or corruption cannot make the parent journal unwritable.
9. Retrying a worker creates a new attempt identity and preserves prior evidence.
10. Concurrency limits are enforced by the runtime, not left to prompts.

### 6.4 Primary States

```text
child: proposed -> ready -> leased -> running
     -> succeeded | failed | cancelled | uncertain

integration: waiting -> reviewable -> planned -> authorized -> applying
           -> verified | conflicted | failed | uncertain
```

### 6.5 Non-Goals

- remote workers;
- organization-level agent pools;
- free-form agent-to-agent messaging outside durable task artifacts;
- shared-workspace parallel writes;
- automatic merge of unverified worker output.

### 6.6 Exit Gate

v0.3 exits when deterministic acceptance scenarios prove parallel observation,
isolated mutation, bounded delegation, cancellation, crash recovery, conflict handling,
budget enforcement, and evidence-linked merge verification on macOS and Linux.

## 7. v0.4 — Provenance Memory

### 7.1 Capability

Yordam can retain and retrieve durable project knowledge across sessions without
turning stale, poisoned, or model-invented memory into silent authority.

### 7.2 Memory Classes

- project facts;
- architecture and policy decisions;
- user preferences;
- task progress and unresolved work;
- failed approaches and operational warnings;
- short-lived scratch notes;
- reusable workflow or skill candidates.

### 7.3 Storage and Retrieval

The append-only journals and immutable evidence remain the source of truth. A searchable
index such as SQLite FTS may be used as a rebuildable projection. Every memory record
contains:

- stable identity and class;
- source session, event, evidence, or user statement;
- source digest and creation time;
- author and extraction method;
- confidence and trust classification;
- scope, expiry, and invalidation conditions;
- contradiction and supersession links;
- last-use and last-validation metadata.

Context reconstruction uses explicit token budgets and reports which sources were
included, summarized, excluded, expired, or contradicted.

### 7.4 Core Invariants

1. Memory is context, not evidence or policy authority.
2. Model-inferred memory is labeled and cannot silently override user-authored facts.
3. Secret-bearing content is rejected or stored only under the existing secret policy.
4. Index loss cannot destroy authoritative history.
5. A memory update preserves the superseded value and provenance.
6. Retrieval decisions are inspectable and reproducible for a pinned runtime generation.
7. Project memory cannot cross canonical workspace boundaries without explicit export.

### 7.5 Non-Goals

- organization-wide knowledge bases;
- implicit cloud synchronization;
- vector-database dependency as a core requirement;
- automatic activation of generated skills or executable workflows.

### 7.6 Exit Gate

v0.4 exits when long-running task scenarios demonstrate deterministic reconstruction,
bounded context injection, stale-memory invalidation, contradiction handling, secret
exclusion, index rebuild, and measurable improvement over session-only context.

## 8. v0.5 — Deterministic Workflows

### 8.1 Capability

Users can run resumable, versioned workflows that coordinate agents, tools, reviews,
verification, and human gates without encoding critical control flow only in prompts.

### 8.2 Workflow Model

The first workflow format is declarative. A workflow graph defines:

- versioned workflow identity and source digest;
- typed nodes and dependencies;
- input and output artifacts;
- selected role, agent, and capability requirements;
- execution profile and permission requirements;
- token, cost, time, retry, and fan-out budgets;
- success, failure, waiver, and cancellation transitions;
- human approval and intervention points;
- verification and final receipt policy.

Executable customization uses the v0.2 hook or MCP boundary. The workflow engine does
not introduce a separate privileged JavaScript plugin runtime.

### 8.3 Built-In Workflows

- `compose`: clarify -> design -> implement -> verify -> review -> integrate;
- `fix`: reproduce -> localize -> test -> repair -> verify -> regress;
- `review`: scope -> inspect -> challenge -> verify -> report;
- `research`: brief -> plan -> collect -> cross-check -> synthesize -> cite;
- `release`: preflight -> build -> verify -> attest -> approve -> publish.

Built-ins are ordinary versioned workflows and do not bypass policy.

### 8.4 Goal Judge and Best-of-N

An independent judge assesses the frozen outcome contract and external evidence. It does
not decide from the assistant's confidence or conversation alone. Best-of-N execution is
available only under an explicit budget and records every candidate, selection criterion,
judge identity, and cost.

### 8.5 Non-Goals

- unbounded autonomous loops;
- workflow code that can grant itself permissions;
- publication or destructive release actions without explicit policy authorization;
- hidden retry of uncertain mutations.

### 8.6 Exit Gate

v0.5 exits when built-in workflows survive process interruption, resume without duplicate
effects, enforce bounded retries and budgets, preserve human gates, and produce complete
workflow receipts across success, failure, cancellation, and uncertain-effect scenarios.

## 9. v0.6 — Code Intelligence

### 9.1 Capability

Yordam understands repository structure, symbols, diagnostics, and likely test impact
well enough to compete on coding quality and efficiency rather than relying only on text
search and shell commands.

### 9.2 Required Surfaces

- opt-in LSP broker and server lifecycle management;
- definitions, references, symbols, implementations, hover, diagnostics, and call hierarchy;
- repository map and dependency projection;
- formatter, linter, type-checker, and test adapter discovery;
- patch/write tool parity with exact previews and stale-preimage protection;
- diagnostic snapshots attached to activities and receipts;
- changed-symbol and test-impact selection;
- bounded web fetch/search through built-in or MCP-backed tools.

### 9.3 Core Invariants

1. LSP and diagnostic servers are project executables subject to trust and authorization.
2. Auto-download or auto-install is disabled unless explicitly authorized.
3. Diagnostics are observations with source/version provenance, not truth by themselves.
4. Structural edits retain exact diff preview, preimage validation, and restore semantics.
5. Fallback to ordinary search and repository commands remains available.
6. Code-intelligence caches are rebuildable and never authoritative session history.

### 9.4 Non-Goals

- embedding every supported language compiler;
- mandatory language-server use for all repositories;
- IDE replacement;
- cloud-only indexing.

### 9.5 Exit Gate

v0.6 exits when a multi-language coding corpus demonstrates correct symbol navigation,
bounded server lifecycle, diagnostic provenance, safe structural edits, and a measurable
completion or efficiency improvement over v0.5 without increasing false verification.

## 10. v0.7 — Local Agent Protocol

### 10.1 Capability

The same trusted Yordam session can be controlled and observed through the TUI, headless
CLI, local SDK, ACP-compatible editor, or another authorized local client.

### 10.2 Architecture

The TUI becomes the default client of a local application service. The v0.2 application
protocol evolves into a stable transport contract with:

- authenticated local connection;
- session create, list, open, fork, attach, and detach;
- vector-cursor snapshot and event catch-up;
- bidirectional permission, question, amendment, and recovery responses;
- capability negotiation and schema-version discovery;
- Go SDK and generated protocol fixtures;
- ACP adapter over stdio;
- headless interactive-control mode distinct from one-way automation mode.

### 10.3 Core Invariants

1. Local protocol access is not implicit authorization for task effects.
2. Every command carries a principal and idempotency identity.
3. Reconnect cannot duplicate a consequential command.
4. Slow or disconnected clients cannot block durable execution indefinitely.
5. Secrets and confidential recovery material are excluded from ordinary client streams.
6. Protocol compatibility is versioned independently from internal Go types.

### 10.4 Non-Goals

- public internet exposure by default;
- team collaboration or RBAC;
- hosted Yordam service;
- first-party desktop application.

### 10.5 Exit Gate

v0.7 exits when TUI, headless, SDK, and ACP conformance suites produce equivalent durable
behavior, survive reconnects, enforce authentication, prevent command duplication, and
honor all v0.2–v0.6 authorization and evidence contracts.

## 11. v0.8 — Enforced Execution

### 11.1 Capability

On supported hosts, users can select an execution backend that provides enforceable
filesystem, process, network, and credential isolation rather than policy-only restriction.

### 11.2 Execution Backends

Yordam defines a pluggable execution-backend contract for:

- trusted host execution;
- restricted but unsandboxed host execution;
- enforced local sandbox;
- disposable local container or virtualized workspace;
- optional remote runner implementations.

Each backend reports supported enforcement capabilities. The runtime rejects a task that
requires an unavailable guarantee rather than silently weakening it.

### 11.3 Core Invariants

1. Execution profile names describe measured enforcement, not marketing intent.
2. Backend capability is probed and included in the runtime generation.
3. Network, credential, mount, process, and persistence capabilities are explicit leases.
4. Cleanup is verified; inability to confirm termination or deletion becomes uncertain.
5. Remote runners do not receive secrets, files, or permissions outside declared inputs.
6. Receipts distinguish Yordam policy, OS enforcement, container isolation, and unknowns.

### 11.4 Non-Goals

- claiming identical isolation across all operating systems;
- silent fallback from sandboxed to trusted host execution;
- fleet scheduling or organization runner pools;
- automatic reversal of external network effects.

### 11.5 Exit Gate

v0.8 exits when supported backends pass adversarial escape, filesystem, network, credential,
process, cancellation, and cleanup suites, while unsupported platforms retain accurate
policy-only labels and fail required-enforcement tasks closed.

## 12. v0.9 — Trusted Ecosystem and Evolution

### 12.1 Capability

Users can discover, inspect, install, share, and improve agents, skills, workflows, hooks,
and tool integrations without bypassing provenance, dependency, trust, and receipt rules.

### 12.2 Package Model

An extension package includes:

- canonical package and publisher identity;
- semantic version and content digest;
- supported Yordam and protocol versions;
- declared agents, skills, workflows, hooks, tools, MCP servers, and provider requirements;
- executable and dependency lock manifests;
- requested capabilities and execution profiles;
- signature and provenance information;
- conformance and security-scan results;
- migration and removal behavior.

Installation is prepare, inspect, authorize, verify, and activate. It is never an opaque
package-manager side effect during application startup.

### 12.3 Trusted Evolution

Session mining may propose:

- memory updates;
- new or revised skills;
- reusable commands;
- workflow candidates;
- agent-definition changes;
- configuration simplification.

Proposals cite their source sessions and evidence, explain expected benefit, pass static
and behavioral checks, and require the same review and authorization as user-authored
project changes. No evolution proposal activates itself.

### 12.4 Compatibility Importers

Yordam may import or reference compatible OpenCode, Claude Code, Codex, and MiMo-Code
instructions, skills, MCP definitions, and agent metadata. Importers produce a preview,
identify unsupported or weakened semantics, and never claim exact compatibility when
permission or lifecycle models differ.

### 12.5 Non-Goals

- arbitrary native in-process plugin ABI;
- unsigned executable auto-installation;
- self-activating model-written code;
- package popularity as a trust signal;
- team-private registry administration.

### 12.6 Exit Gate

v0.9 exits when package install/update/remove, signature failure, dependency drift, trust
revocation, compatibility import, and evolution-proposal scenarios are deterministic,
recoverable where promised, and fully represented in receipts.

## 13. v1.0 — Verified Agent Platform

### 13.1 Capability

Yordam v1.0 is a stable local agent platform whose autonomy, safety, compatibility, and
performance claims are supported by reproducible release and benchmark evidence.

### 13.2 Stability Contract

v1.0 freezes supported compatibility policies for:

- configuration schema;
- durable event and evidence formats;
- session lineage and migration;
- application protocol and SDK;
- workflow schema;
- extension package manifest;
- agent, skill, hook, provider, tool, and MCP identities;
- authorization and receipt schemas;
- documented CLI commands and exit categories.

Future change remains possible through explicit version negotiation, migration, and
deprecation windows. Internal Go APIs are not public merely because they exist.

### 13.3 Release Proof

The v1.0 release candidate must provide:

- full migration fixtures from every public Yordam release;
- macOS and Linux release evidence for supported architectures;
- independent security review and resolved critical findings;
- crash, corruption, concurrency, secret, sandbox, and recovery suites;
- provider, MCP, ACP, SDK, workflow, and extension conformance suites;
- reproducible benchmark results against pinned competitor versions;
- documented performance and resource envelopes;
- complete operator, extension-author, and protocol documentation;
- signed archives, checksums, SBOMs, and provenance attestations.

### 13.4 v1.0 Non-Goals

- first-party desktop application;
- team workspaces, RBAC, SSO, or fleet policy;
- hosted cloud control plane;
- universal remote execution;
- guaranteed reversal of arbitrary external effects.

## 14. Benchmark and Evaluation Program

### 14.1 Purpose

`yordam-bench` begins with v0.3 and evolves with every release. It measures whether a
new capability improves useful autonomy without weakening trustworthiness.

### 14.2 Fair-Comparison Contract

Yordam, OpenCode, and MiMo-Code are compared using the same:

- repository snapshot and clean-room reset;
- task prompt and observable completion criteria;
- provider, model, reasoning setting, and context limits;
- token, cost, time, tool-call, and concurrency budgets;
- network and external-service availability;
- number of independent attempts;
- external verifier and result-classification rules.

Competitor versions, configuration, prompts, and enabled extensions are pinned and
published with the result. Planned Yordam behavior is never scored as shipped behavior.

### 14.3 Task Families

- localized bug fix;
- cross-package bug fix;
- feature implementation;
- refactor with preserved behavior;
- test generation and regression prevention;
- code review and defect discovery;
- dependency or configuration migration;
- repository research and explanation;
- long-running task with context pressure;
- multi-agent decomposable task;
- permission denial, cancellation, crash, and recovery scenarios;
- adversarial instruction, tool, extension, and memory inputs.

### 14.4 Reported Dimensions

No single composite score is authoritative. Results report:

- externally verified completion rate;
- false completion and false verification rate;
- interventions per verified task;
- permission decisions by risk class;
- wall time, provider latency, token usage, and cost;
- tool and worker efficiency;
- recovery and restore success;
- uncertain and irreversible effect rate;
- reproducibility across attempts;
- security and policy violations.

The primary strategic plot reports autonomy and trustworthiness separately. Numeric
release targets are calibrated from the v0.2 pilot and the first pinned competitor run;
targets are then frozen in the acceptance specification for the release that claims them.

## 15. Delivery and ECC Operating Model

### 15.1 Daily Surfaces

The repository's daily engineering lane uses:

- Go patterns and Go testing guidance;
- test-driven development;
- security review;
- verification loop;
- error-handling and hexagonal-architecture review;
- Go-specific code review;
- `scripts/check.sh` as the canonical repository verification command.

### 15.2 On-Demand Library Surfaces

Use on demand:

- agent harness construction and architecture audit;
- benchmark methodology and agent evaluation;
- native provider integration;
- MCP client and protocol work;
- performance profiling and optimization;
- production and release audit;
- specialized failure and silent-error review.

Node-oriented ECC hooks are not installed as a second runtime. Useful concepts such as
quality gates, configuration protection, MCP health, and continuous learning are
implemented through Yordam's native Go, hook, evidence, and receipt contracts.

## 16. Cross-Release Invariants

All releases preserve these rules:

1. No consequential side effect precedes durable authorization.
2. Model text alone cannot verify an outcome.
3. Authentication never implies action authorization.
4. Memory and extension content are untrusted inputs, not policy.
5. Unsupported required capabilities fail visibly without silent semantic emulation.
6. Every retry of an uncertain mutation is a new explicit activity.
7. Recovery never rewrites source history.
8. Restore claims only effects for which exact coverage exists.
9. Active semantic runtime generations remain immutable.
10. Resource and concurrency budgets are runtime-enforced.
11. No child agent, workflow, plugin, hook, or client can broaden user hard-deny policy.
12. Unknown and externally unverifiable effects remain visible in receipts.

## 17. Major Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Roadmap becomes a perpetual rewrite | No usable releases | One primary thesis and independent exit gate per minor release |
| Feature parity erodes trust model | Yordam loses its differentiation | Capability admission contract and retained v0.2 invariants |
| Multi-agent concurrency corrupts work | Lost or conflicting changes | Immutable inputs, isolated mutation workspaces, separately verified integration |
| Memory poisons later decisions | Persistent incorrect behavior | Provenance, expiry, contradiction tracking, non-authoritative memory policy |
| Workflow loops waste money or repeat effects | Cost and safety failure | Runtime budgets, bounded retries, durable attempt identity, no automatic uncertain mutation retry |
| LSP and plugins execute untrusted code | Host compromise | Project trust, executable manifests, capability leases, sandbox backends |
| Server surface expands attack area | Unauthorized local control | Authenticated local transport, principal binding, idempotency, protocol fuzzing |
| Ecosystem becomes a supply-chain vector | Malicious extension execution | Signatures, locks, provenance, inspection, conformance, explicit activation |
| Benchmark favors Yordam-specific workflows | Misleading superiority claim | Same model/budget/snapshot, public tasks, pinned configs, external verifiers |
| v1.0 promises too much compatibility | Frozen accidental internals | Explicit public contracts and versioned negotiation; internal Go APIs excluded |

## 18. Design Approval and Next Handoff

This roadmap is approved at the strategic level. After the written specification passes
user review, the next artifact is an implementation roadmap plan. That plan must:

1. map v0.2 completion dependencies into the v0.3 start gate;
2. define one implementation and acceptance plan per minor release;
3. begin the benchmark harness before making competitive superiority claims;
4. avoid implementation work for later releases before the current release gate passes;
5. preserve the cross-release invariants and capability admission contract above.
