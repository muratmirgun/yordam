## 1. Decision Summary

Yordam v0.3 makes Yordam capable of developing Yordam through its own terminal
interface. A user can run a long coding session, compact its context without
rewriting history, load local procedural skills with explicit provenance, and
delegate one bounded task at a time to a local child session before resuming the
parent turn.

The release thesis is:

> Yordam can use its existing read, search, edit, shell, session, authorization,
> journal, and recovery foundations to perform a real change in its own repository,
> retain the working context across compaction and restart, and obtain focused help
> from one inspectable child agent.

v0.3 is not a broad multi-agent platform release. It deliberately chooses one
sequential child over parallel workers and uses the existing `auto` mode plus
trusted-shell acknowledgement instead of introducing another full-access mode.

## 2. User-Visible Capability

After v0.3, a user can:

1. start Yordam in a repository and use the existing coding tools to inspect,
   modify, format, test, and review that repository;
2. run `/compact` manually and optionally compact automatically before a known
   model context window is exhausted;
3. add a global or project `SKILL.md`, inspect its identity and trust state, and
   let the model load it only when relevant;
4. let the parent agent delegate a focused task to one local child session;
5. inspect the child session and its result before the parent continues;
6. stop Yordam and resume with `--continue` without losing the accepted compaction,
   skill provenance, parent-child lineage, or terminal child result.

## 3. Current Baseline

The current production runtime already exposes four built-in tools:

- `read`: bounded UTF-8 text reads with stable line numbers;
- `search`: deterministic fixed-string search;
- `edit`: exact, preimage-bound replacements and creation of one text-file leaf;
- `shell`: cancellable, bounded, trusted unsandboxed shell execution.

The current permission modes remain normative:

- `safe` allows observation inside the workspace and denies mutation;
- `ask` asks before mutation or outside access;
- `auto` allows trusted built-in workspace edits and asks once before trusted local
  shell execution is acknowledged for the session.

The current `/compact` command is only a presentation and application seam. The
production runtime does not provide a compaction service, so the command returns
`compaction is not configured`. v0.3 closes that product-contract defect.

## 4. Goals and Exit Metrics

### 4.1 Goals

- Make manual compaction a real, durable production operation.
- Prevent known context exhaustion with an optional automatic trigger.
- Add non-executable, provenance-bound global and project skills.
- Add one sequential, depth-one local child session.
- Preserve v0.2 authorization, journal durability, recovery, secret-admission, and
  runtime-generation boundaries.
- Prove the combined capability against the Yordam repository itself.

### 4.2 Exit Metrics

v0.3 exits only when:

1. the self-hosting acceptance scenario in Section 15 passes on macOS and Linux;
2. every new provider egress and mutation is ordered after durable authorization;
3. a failed or cancelled compaction leaves the previously usable context unchanged;
4. a project skill cannot become model-visible without the configured trust decision;
5. a child cannot exceed the parent policy ceiling or create another child;
6. restart recovery never silently repeats an uncertain child mutation;
7. all v0.1 and v0.2 Foundation regression suites remain green.

## 5. Non-Goals

v0.3 does not add:

- parallel child agents;
- child worktrees or remote workers;
- delegation depth greater than one;
- free-form agent-to-agent messaging;
- separate primary agent roles such as Build and Plan;
- a new `full` or permission-bypass mode;
- new mandatory write, delete, move, glob, regex, LSP, web, MCP, plugin, or patch
  tools;
- executable skills, hooks, marketplace installation, URL installation, or
  model-authored skill installation;
- deletion or rewriting of source journal history during compaction;
- automatic acceptance of a child completion claim as parent-task verification.

## 6. Cross-Capability Invariants

1. Existing source journal events are immutable.
2. No provider, tool, file, process, trust, or child-start effect begins before its
   ordinary authorization and durable activity boundary.
3. Skills, compaction summaries, and child output are context inputs, never policy.
4. A runtime generation freezes model, tool, skill-catalog, and policy semantics for
   the active turn.
5. Reloaded files affect only a future runtime generation and future turns.
6. The parent and child never mutate the shared workspace concurrently.
7. Child identity, lineage, terminal cursor, and receipt remain inspectable.
8. Retry creates a new activity or child identity and preserves earlier evidence.
9. Unknown effects remain visible and are not automatically repeated.
10. Secrets pass through the existing admission and redaction boundaries before
    provider context, ordinary evidence, logs, or TUI output.

## 7. Architecture

Yordam remains a modular Go monolith. The existing application protocol, journal,
orchestrator, provider, tooling, authorization, evidence, recovery, and TUI layers
remain the shared foundation.

Three bounded capabilities are added:

- `compaction`: selects an immutable historical range, produces a bounded summary,
  stores summary evidence, and commits one compaction projection event;
- `skills`: discovers, validates, identifies, trusts, snapshots, lists, and loads
  instruction-only skill packages;
- `subagent`: coordinates one parent pause, one child session, and one terminal
  result attachment at a time.

The application composes these services into the active runtime generation. No
service receives raw journal append authority except through the existing
orchestrator and repository boundaries.

## 8. Compaction

### 8.1 Surfaces

- `/compact` starts a manual compaction while the selected session is idle.
- The context planner may request automatic compaction immediately before a new
  provider request when the selected model has a known context window.
- The context panel shows whether auto-compaction is available, the estimated
  context usage, and the manual `/compact` action.

### 8.2 Selection and Summary

Compaction retains the active task, unresolved approvals, recent user and assistant
messages, recent tool results required by those messages, and every fact after the
selected compaction boundary. It selects an older, contiguous, committed cursor
range for summarization.

Before summarization, large tool-result bodies are replaced in model context by
their existing artifact and evidence references. The underlying journal events and
artifact bytes are not deleted.

The summary must preserve, when present:

- the user's goal and explicit constraints;
- decisions and their reasons;
- files inspected or changed;
- commands and tests run, including failures;
- unresolved questions and remaining work;
- child-session identities and terminal result references;
- skill identities used in the compacted range;
- unknown or unverifiable effects.

The summary is capped at the existing `128 KiB` bound. It is stored as immutable
evidence before a `context_compacted_v1` event references its digest and exact source
cursor range.

### 8.3 Context Reconstruction

At reconstruction time, the latest valid compaction contributes:

1. its provenance-bearing summary;
2. the uncompacted journal suffix after its terminal cursor;
3. any active runtime instructions and explicitly loaded skill content.

A later compaction may include the prior summary as an input. It never claims that
the summary is the original evidence.

### 8.4 Manual and Automatic Triggering

Manual compaction works without a configured model context window by using a
conservative bounded summarization input. If the provider refuses that input, the
operation fails visibly and commits no new compaction projection.

Automatic compaction is enabled by default only when the selected model declares a
positive `contextWindow`. It triggers before provider dispatch when:

```text
estimated_input_tokens + output_reserve >= context_window - compact_reserve
```

The default compact reserve is ten percent of the declared window with a minimum of
2,048 tokens. Configuration may disable auto-compaction or set an explicit reserve.
If the reserve plus output reserve cannot fit below the declared window, automatic
compaction is unavailable and validation reports the incompatible values.

A provider `context_too_large` result does not cause a silent retry. Yordam reports
the failure and offers `/compact`.

### 8.5 Lifecycle and Failure

```text
planned -> authorized -> summarizing -> persisted -> committed
                                  \-> failed | cancelled | uncertain
```

- Provider egress follows the ordinary authorization and activity path.
- Cancellation before commit leaves the prior context projection active.
- Evidence persistence or journal commit failure does not expose a partial summary
  as active context.
- Repeating the same request against the same source cursor is idempotent.
- An uncertain provider request is not resent automatically.
- Compaction can run only while no turn, reload, or child is active.

## 9. Skills

### 9.1 Package Layout

Project skills live at:

```text
.yordam/skills/<name>/SKILL.md
```

Global skills live at:

```text
~/.config/yordam/skills/<name>/SKILL.md
```

The minimum file format is:

```markdown
---
name: go-testing
description: Test and verify Go changes.
---

Skill instructions...
```

The directory name and frontmatter name must match. Names use lowercase ASCII
letters, digits, and single hyphens. Descriptions are plain text and bounded.

### 9.2 Identity and Discovery

Each skill identity binds:

- canonical name;
- source class: `global` or `project`;
- canonical regular-file path;
- workspace identity for project skills;
- content digest;
- active runtime-generation identity.

Discovery rejects symlinks, path traversal, non-regular files, non-UTF-8 content,
invalid or duplicate frontmatter, and files larger than `128 KiB`. A catalog contains
at most 128 active skills.

Global skills are active user-managed input. Project skills are discovered but are
not exposed to the model until the configured project-skill policy resolves.

### 9.3 Trust

Project skill policy is one of:

- `ask`: require a visible workspace trust decision before activation;
- `allow`: activate valid project skills for the canonical workspace;
- `deny`: keep project skills unavailable.

Trust decisions bind the canonical workspace and catalog digest and are stored in the
workspace-control journal. A changed digest is a new catalog decision. Project trust
never changes file, shell, provider, or child permissions.

### 9.4 Catalog and Loading

The system prompt receives only the active skill names, descriptions, sources, and
digests. A built-in read-only `skill` tool loads the complete content by canonical
name when the model decides it is relevant.

The load result includes the canonical identity and provenance. Skill content enters
the current context as untrusted instructions beneath system, user, and permission
policy. It cannot grant capabilities or suppress approval.

The `skill` tool accepts only an identity from the frozen active catalog. It does not
accept a filesystem path and cannot be used as a generic outside-workspace reader.

If a project and global skill share a name, the trusted project skill shadows the
global skill. `/skills` displays both records and the shadowing relation. Duplicate
names inside one source class are an error rather than a nondeterministic choice.

### 9.5 Runtime Immutability and Reload

A runtime generation holds an immutable skill-catalog snapshot. Editing a `SKILL.md`
during an active turn does not change that turn. `/reload` validates a candidate
catalog and activates it only for future turns. A failed reload preserves the prior
complete runtime generation.

Child sessions receive the exact parent skill-catalog snapshot. They do not perform
independent discovery during the delegated task.

## 10. Sequential Subagent

### 10.1 Tool Contract

The parent model receives one built-in `subagent` tool:

```text
subagent({
  task: string,
  expected_output?: string,
  context?: string
})
```

`task` is required and describes one bounded objective. `expected_output` describes
the desired result shape. `context` carries a bounded parent-authored handoff and is
not authority. The first release always uses the parent's selected provider and
model.

### 10.2 Identity and Lineage

Every accepted request creates:

- a new child session ID;
- an immutable parent session and cursor reference;
- a child task and turn identity;
- a delegation attempt identity;
- the parent runtime-generation and skill-catalog identities;
- child tool-call and wall-time limits.

The child journal owns child provider calls, tool activities, evidence, usage, and
terminal result. The parent journal owns the request, waiting state, and exact child
terminal-result attachment.

### 10.3 Parent and Child Flow

```text
parent running
  -> child requested and committed
  -> parent waiting_for_child
  -> child running
  -> child terminal receipt committed
  -> parent result attached
  -> parent running
```

The parent commits the request and waiting state before the child begins. It then
releases or transfers the shared operation lane so the child can use the ordinary
orchestrator. The parent provider continuation remains paused.

When `subagents.enabled` is true, creating the child is an ordinary configured-provider
operation rather than a permission bypass. It follows the existing provider
authorization path and the runtime budgets below. Every child tool action still
resolves independently through the inherited permission ceiling.

Only the child may own the mutation lane while it is active. After the child terminal
receipt is durable, the parent reacquires the lane, records the exact child cursor and
receipt digest idempotently, and presents the result as the `subagent` tool result to
the parent provider continuation.

There is no cross-journal atomic transaction. Recovery observes child terminal state
through exact identities and cursors.

### 10.4 Limits

- Maximum delegation depth: `1`.
- Maximum active children per parent: `1`.
- Maximum child attempts per parent turn: `4`.
- Default child tool-call limit: `16`, configurable from `1` to `64`.
- Default child wall-time limit: `10 minutes`, configurable up to `30 minutes`.
- A child cannot see or invoke the `subagent` tool.
- A retry creates a new child session and attempt identity.

### 10.5 Permission Inheritance

The child inherits:

- the parent permission mode as a ceiling;
- platform and project hard-deny policy;
- canonical workspace boundary;
- provider and tool catalog from the frozen runtime generation.

The child does not inherit:

- allow-once decisions;
- exact session grants;
- trusted-shell acknowledgement;
- unresolved parent approvals.

Child approval requests appear in the parent TUI with the child identity. A session
grant issued there applies only to that child session. The child cannot amend parent
policy or make an outside-workspace action automatic.

### 10.6 Terminal Result

A child result has one status:

- `succeeded`;
- `failed`;
- `cancelled`;
- `uncertain`.

The result records:

- a bounded summary;
- child session, task, turn, attempt, and terminal cursor identities;
- changed files reported by workspace inspection;
- commands and tests observed in child activities;
- provider and tool usage available from durable records;
- verification evidence and explicit unknown effects;
- error or cancellation detail.

The result is evidence-bearing input. `succeeded` does not verify the parent task and
does not authorize another action.

### 10.7 Cancellation and Recovery

- `Esc` cancels the active child and the waiting parent operation.
- Child cancellation uses the existing provider and process-group cancellation path.
- If a child receipt is terminal after restart, the parent attaches it idempotently.
- If restart finds a nonterminal child with no unmatched effect, recovery terminalizes
  it as interrupted rather than resuming it invisibly.
- If the child ended during an unproven mutation, recovery marks the attempt
  `uncertain` and does not repeat it.
- A failed child cannot make the parent journal unwritable.
- Retry is explicit and always creates a new child identity.

## 11. TUI

### 11.1 Compaction

`/compact` shows:

- preparation, summarization, persistence, and completion progress;
- the compacted cursor or message range;
- whether the trigger was manual or automatic;
- the resulting summary size and provider usage when known;
- actionable failure or cancellation detail.

### 11.2 Skills

`/skills` shows:

- name and description;
- global or project source;
- active, denied, awaiting-trust, invalid, or shadowed state;
- short content digest;
- project trust action when required.

### 11.3 Child Sessions

The parent conversation shows a child card containing:

- task summary and child session ID;
- running or terminal state;
- tool-call and elapsed-time budget;
- changed-file and test summary;
- navigation into the child session.

The existing session browser includes parent-child lineage. No separate transient
navigation model is introduced.

## 12. Configuration Contract

The JSONC configuration gains additive fields equivalent to:

```jsonc
{
  "model": "provider/model-id",
  "provider": {
    "provider": {
      "models": {
        "model-id": {
          "contextWindow": 128000
        }
      }
    }
  },
  "context": {
    "autoCompact": true,
    "compactReserveTokens": 12800
  },
  "skills": {
    "projectPolicy": "ask"
  },
  "subagents": {
    "enabled": true,
    "maxPerTurn": 4,
    "maxToolCalls": 16,
    "timeoutSeconds": 600
  }
}
```

Rules:

- `contextWindow` is optional and must be positive when present.
- `autoCompact` defaults to true but is effective only with a known context window.
- `compactReserveTokens` is optional; the default follows Section 8.4 and it must be
  smaller than the declared context window.
- `projectPolicy` defaults to `ask` and accepts only `ask`, `allow`, or `deny`.
- subagents default to enabled with the limits in Section 10.4.
- `/reload` validates all new values as one candidate runtime generation.
- Invalid candidate configuration preserves the active generation.

## 13. Compatibility and Migration

- Event envelope version remains `2`.
- Application protocol version remains `1` and gains additive capability flags and
  command payloads.
- New payloads begin at version `1`.
- Existing v0.1 and v0.2 sessions remain readable.
- Valid legacy compaction events remain context inputs but cannot claim the new
  evidence and cursor coverage they do not contain.
- Existing sessions without skill, child, or native compaction events behave exactly
  as before.
- No stored session is rewritten during migration or projection rebuild.

## 14. Testing Strategy

### 14.1 Compaction

- manual success and repeated idempotent request;
- automatic threshold and disabled/unknown-window behavior;
- prior summary plus uncompacted suffix reconstruction;
- large tool-output reference preservation;
- provider failure, cancellation, evidence failure, and journal commit uncertainty;
- restart after evidence persistence and before or after event commit;
- secret redaction across prompt, summary, evidence, logs, and TUI.

### 14.2 Skills

- global and project discovery;
- project trust allow, ask, deny, and changed-digest behavior;
- project-over-global shadowing and duplicate rejection;
- malformed frontmatter, non-UTF-8, oversized files, symlink, and path traversal;
- immutable active-turn catalog and `/reload` activation;
- full-content load with identity and provenance;
- attempted permission override remaining ineffective;
- identical parent and child catalog snapshots.

### 14.3 Subagents

- read-only investigation;
- child edit followed by focused test;
- parent permission ceiling and child-specific approval;
- trusted-shell acknowledgement not inherited;
- depth and one-active-child enforcement;
- tool-call and wall-time exhaustion;
- cancellation of provider and shell work;
- child success, failure, cancellation, and uncertain mutation;
- restart before child start, during child execution, after child receipt, and before
  parent attachment;
- idempotent terminal attachment and explicit retry identity;
- parent continuation receiving the exact terminal result.

### 14.4 Regression

Every implementation task runs focused tests, `go test ./...`, `go test -race ./...`,
`go vet ./...`, and `git diff --check` in proportion to the task. The release gate
also reruns the existing v0.1 and v0.2 Foundation acceptance suites.

## 15. Self-Hosting Acceptance Scenario

The release proof runs Yordam from a disposable clean checkout of the Yordam
repository and records one exact source commit and deterministic provider fixtures
where external credentials are not needed. The acceptance harness never mutates the
developer's primary checkout.

1. Start Yordam in `auto` mode at the repository root.
2. Discover and explicitly trust a project Go-development skill.
3. Ask the parent to make a bounded repository change.
4. Have the parent delegate code investigation to one child.
5. Have the child read and search source, edit or create a file, and run a focused
   test through the ordinary permission system.
6. Attach the child receipt and let the parent inspect the change and run the complete
   verification command.
7. Compact the session and record the exact compacted range and summary digest.
8. Stop Yordam and resume with `--continue`.
9. Prove that the accepted compaction, skill provenance, parent-child lineage,
   terminal child result, and workspace state remain available.
10. Prove that source journals were not rewritten and no uncertain effect was retried.

The matrix also covers denied project trust, malformed skill, provider compaction
failure, child timeout, user cancellation, and crash recovery. It runs on supported
macOS and Linux release targets.

## 16. Implemented Delivery Order

1. Add native compaction protocol, service, production wiring, and acceptance tests.
2. Add skill identity, discovery, trust, catalog, load tool, `/skills`, and tests.
3. Add sequential child protocol, coordinator, permission routing, child card, and
   recovery tests.
4. Add the combined self-hosting acceptance fixture and release evidence.
5. Update README, SECURITY, configuration schema, generated template, help, and
   changelog to match production behavior exactly.

Each stage is independently testable. Skills do not depend on subagents. Subagents
consume the already-complete skill-catalog snapshot. The combined acceptance stage
does not begin until all three capabilities pass their focused suites.

## 17. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Compaction hides unresolved work | Parent proceeds with incomplete context | Required summary fields, exact cursor range, retained suffix, source history preserved |
| Summary contains a secret | Secret persists or reaches provider | Existing admission/redaction on input and all output surfaces |
| Repository skill injects hostile instructions | Unsafe model behavior | Explicit project trust, provenance, no authority, normal action permissions |
| Skill changes during a turn | Non-reproducible behavior | Immutable runtime-generation catalog snapshot |
| Parent and child both mutate the workspace | Corruption or nondeterministic state | One active child and exclusive lane transfer |
| Child loops or consumes excessive resources | Cost and latency failure | Depth one, attempt/tool/time limits, cancellation |
| Crash loses child result | Duplicate work or orphan state | Child receipt first, exact cursor attachment, idempotent recovery |
| `auto` becomes an implicit permission bypass | Unexpected host mutation | Existing trusted-shell warning and no new bypass mode |
| Scope expands toward OpenCode parity | v0.3 never ships | Explicit non-goals and one self-hosting exit scenario |
