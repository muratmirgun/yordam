# Feature Spec: Yordam v0.2 Trust Loop

Status: approved design
Date: 2026-07-17
Parent PRD: [Yordam v0.2 Trusted Extensibility](2026-07-17-yordam-v0.2-prd.md)
Normative contract: [Yordam v0.2 Capability Contract](2026-07-17-yordam-v0.2-capability-contract.md)

Internal gate: 2 of 4

## 1. Purpose

Trust Loop makes one agent understandable, permissioned, recoverable, and verifiable before extensibility increases the number of trust boundaries. It introduces task outcome contracts, the operator cockpit, risk-aware permissions, checkpoints, immutable forks, exact built-in edit restore, verification receipts, and usage visibility.

The release continues to run one active turn with sequential effects. Trust Loop does not add subagents, task DAGs, parallel tools, or a steering queue.

## 2. User Promise

At any point in a task, the user can determine:

- the goal and completion criteria;
- the active turn phase and action;
- the action's declared purpose;
- the system-observed evidence;
- the effective permission and risk boundaries;
- the resulting changes and verification coverage;
- the latest eligible checkpoint, its per-subject coverage, unresolved external effects, and available recovery choices.

## 3. Outcome Contract

### 3.1 Creation

A task begins with:

- required goal text;
- zero or more user-provided completion criteria;
- optional constraints, such as prohibited files or no public API changes.

Goal and the user's initial draft become durable first. If required criteria are missing, Yordam enters `contract_drafting`: the selected provider receives the goal and draft, mutation-capable tools are absent, and any discovery tool is observation-only and passes normal authorization. The agent then proposes observable criteria. Proposed criteria identify:

- required behavior or postcondition;
- verification method;
- expected evidence kind;
- whether human judgment remains necessary.

The proposed contract is visible and requires an explicit user freeze in the TUI. Headless input must include at least one required criterion; otherwise headless exits with a contract-required `RunReceipt` before any provider request. Read-only discovery may occur before freeze only when necessary to make criteria observable, and those activities remain in the ledger. A frozen contract with zero required criteria is invalid.

### 3.2 Freeze and Amendment

The active contract freezes before the first mutation. Once frozen:

- required criteria cannot disappear silently;
- optionality cannot change silently;
- verification methods cannot be weakened silently;
- agent-proposed amendments are visible and require user approval when they reduce or materially change required outcomes;
- user amendments are durable and identify which subsequent activities use the new version.

Pure clarifications that do not change success semantics may be recorded without a new required approval but still create a versioned amendment event.

### 3.3 Assessment

Criterion status values are:

- `pending`;
- `verified`;
- `failed`;
- `unknown`;
- `waived_by_user`.

The task terminal status is:

- `verified`: every required criterion has evidence-backed `verified` status;
- `completed_with_waivers`: all non-waived required criteria are verified and at least one required criterion is explicitly waived;
- `partial`: at least one required criterion is verified and at least one remains failed or unknown;
- `failed`: execution or a required criterion failed with no verified task outcome;
- `unknown`: the turn ended but evidence cannot establish required criteria;
- `cancelled`: the user or runtime cancelled before terminal assessment.

Waivers remain visible in the final receipt, do not become `verified` evidence, and are excluded from the verified-completion metric. A `partial`, `failed`, `unknown`, or `completed_with_waivers` task may be explicitly reopened for a new turn; the prior assessment remains immutable history.

## 4. Operator Cockpit

### 4.1 Wide Layout

At 120 columns and wider, the conversation screen uses:

1. a two-row status header;
2. a task band containing goal, criterion progress, active checkpoint, and task verification state;
3. an activity ledger occupying approximately two-thirds of the body;
4. an inspector occupying approximately one-third;
5. the composer below the body.

The header shows:

- session and fork identity;
- canonical workspace;
- effective permission mode;
- selected agent;
- provider/model;
- effective execution profile;
- context-window consumption;
- token and cost state;
- active recovery or read-only warning.

The inspector has views for `Now`, `Evidence`, `Changes`, `Decision`, `Verification`, and `History`. Required attention, mutation uncertainty, errors, and recovery automatically select the relevant inspector view. Ordinary read-only activity remains collapsed unless selected.

### 4.2 Narrow Layout

Below 120 columns:

- the activity stream remains the home surface;
- inspector, permission, diff, checkpoint, restore, and recovery surfaces replace the stream temporarily;
- breadcrumbs identify task, turn, activity, and queue position;
- closing a non-blocking surface restores stream scroll, focus, and draft;
- the composer is hidden on blocking permission surfaces and restored unchanged afterward;
- security-critical fields wrap or scroll and are never silently middle-truncated.

Status-path display may truncate. Canonical scopes, commands, risk warnings, decision lifetime, and unknown-effect warnings must remain fully inspectable.

### 4.3 Activity Cards

Every consequential activity card contains:

#### Purpose

- concise relation to the task goal or criterion;
- source actor;
- explicit label that it is an agent or system claim rather than evidence.

#### Evidence

- exact redacted input or command;
- canonical structured scope;
- local or remote source;
- proposed or actual diff;
- output excerpts and artifact links;
- timestamps, duration, exit status, hashes, truncation, and usage where relevant.

#### Decision

- effect class and risk axes;
- policy source and reason;
- human or policy actor;
- allow, deny, ask, or cancellation outcome;
- exact authorized resource and plan digest;
- once or session lifetime;
- revocation state.

#### Verification

- observed postconditions;
- receipt and evidence links;
- verified criteria;
- unknown, external, or uncovered effects;
- whether exact restore material exists.

No raw chain-of-thought field exists.

## 5. Turn and Activity Visibility

The cockpit exposes these authoritative phases:

```text
idle
-> drafting/freezing contract
-> preparing context
-> waiting for provider
-> receiving provider
-> preparing action
-> awaiting permission
-> executing
-> recording evidence
-> returning result
-> verifying
-> completed | failed | interrupted
```

Provider retries before the first delta show attempt count and bounded backoff. After content is emitted, an automatic fresh attempt is prohibited and the interruption remains visible.

The composer may retain a next-turn draft while a turn is active. It does not queue a second prompt and does not steer the active turn. Mode and model changes requested during a turn show as next-turn changes.

## 6. Risk-Aware Permission Queue

### 6.1 Risk Axes

Risk is displayed through independent facts rather than one color or score:

- **Effect:** observation, local file mutation, process execution, or remote mutation;
- **Boundary:** inside workspace, outside workspace, network target, or remote resource;
- **Execution locus:** Yordam built-in, local process, local MCP, remote MCP, or hook;
- **Reversibility:** exact, detectable-only, unknown, or not reversible by Yordam;
- **Verification coverage:** exact postcondition, partial observation, server response only, or unknown.

Color supplements text and never carries the only risk meaning.

### 6.2 Initial Risk Classes

| Class | Typical Action | Default Meaning |
|---|---|---|
| R1 | Built-in read/search inside workspace | Observation; selected data may reach the model provider |
| R2 | Read/search outside workspace or intentional egress | Boundary-crossing observation or disclosure |
| R3 | Built-in edit inside workspace | Controlled mutation with exact path, diff, and restore material |
| R4 | Built-in edit outside workspace | Boundary-crossing mutation with separate preview inspection and write decisions |
| R5 | Shell, command hook, local MCP process effect, network action, or remote mutation | Effects may escape workspace and may be unknown or irreversible |

The class is a summary. The five axes remain authoritative.

### 6.3 Queue Semantics

1. The queue belongs to one session, task, and turn.
2. Model-provided actions remain in model order.
3. Only prepared, canonicalized requests enter the queue.
4. Only the first unresolved request is actionable; later requests are summaries and never start early.
5. No heterogeneous bulk approval exists.
6. Denying one request does not implicitly deny siblings.
7. `Deny remaining` and `Cancel turn` are separate explicit actions.
8. A decision becomes durable before execution; an allow-once decision is atomically consumed by the matching activity-start commit.
9. Turn cancellation terminalizes unresolved queue entries as `cancelled`, not user-denied.
10. Permission prompts are not resumed as actionable prompts after restart.
11. A stale call ID, changed plan digest, changed tool identity, or changed canonical scope cannot authorize execution.
12. Session switch, fork, rewind, and restore are blocked while permission or execution is active.

Outside edit preview may require one authorization for boundary-crossing read inspection and another for the exact write. The two decisions must not be collapsed.

### 6.4 Decision Lifetimes

- `Allow once` authorizes one exact plan digest, call identity, and canonical resource set.
- `Allow for session` authorizes the displayed future capability for the same canonical tool and structured scope.
- `Deny` resolves only the current request unless the user explicitly adds a policy rule.

For example, a session edit grant for a file permits future built-in edits to that exact file, not only the currently displayed diff. The UI must say so before approval.

Active grants are inspectable and revocable. Revocation increments a live deny epoch checked before every dispatch, including within an active turn. It blocks a new action without mutating that turn's frozen semantic runtime generation.

### 6.5 Control-Operation Decisions

Reload, MCP connect/auth/catalog refresh, project-trust, credential, and recovery work appears as a serialized `ControlOperation` card with the same five risk axes. A control operation always has workspace, control-operation, activity, queue, plan, policy, and runtime-generation identity. It may be taskless or carry optional task/turn/activity causation when a turn requested it, but its durable lifecycle remains in the workspace control journal. It cannot run concurrently with another consequential operation. In headless mode, an unresolved control-operation `ask` fails closed.

### 6.6 Broad Trusted-Shell Acknowledgement

Broad trusted-shell acknowledgement is not an ordinary exact command grant. It requires a separate confirmation that states:

> Enable future unsandboxed shell calls for this session under trusted-local policy. Commands may read or write outside the workspace, access the network, launch processes, and use non-provider environment values.

The acknowledgement remains visible in status, is revocable, resets when leaving the applicable mode, and never survives a fork.

## 7. Execution Profiles

### 7.1 `restricted local`

This profile applies conservative authorization defaults:

- in-workspace built-in observations may be allowed;
- boundary-crossing reads ask or deny according to mode;
- built-in mutations ask or deny unless existing mode policy explicitly permits them;
- arbitrary process, network, command-hook, and local-MCP execution asks or denies;
- project sources remain inactive without workspace trust.

### 7.2 `trusted local`

This profile permits broader actions only after visible, durable acknowledgement. It does not change the underlying process confinement: execution still uses the user's privileges unless a future OS sandbox backend exists.

The requested and effective profile are part of the activity and receipt. No UI string may abbreviate either profile to `sandboxed` or `isolated`.

## 8. Checkpoints

### 8.1 Automatic Creation

After a canonical mutation plan and plan digest are durable, a checkpoint is prepared before every consequential mutation, including built-in edits and approved restore operations. It becomes selectable only after all required records and confidential restore material are durable. Any later plan or resource change invalidates the checkpoint for that action.

Checkpoint metadata includes:

- checkpoint, session, task, turn, and event-head identity;
- creation actor and time;
- immutable context-plan manifest and digest, including exact included content or immutable evidence references, precedence, compaction version, catalog alias mapping, and model descriptor facts;
- active outcome-contract version;
- model, mode, execution profile, and runtime generation;
- evidence links;
- workspace coverage entries;
- external-effect coverage classification;
- completeness and recovery state.

### 8.2 Coverage Classes

- `context_exact`: session projection and every context-plan dependency through the checkpoint can be resolved and digest-verified.
- `exact_edit_restore`: complete confidential built-in edit preimages exist for named supported subjects.
- `drift_detectable`: fingerprints exist but full restore content does not.
- `external_unknown`: effects may exist but Yordam cannot enumerate or reverse them.
- `not_reversible`: known remote or external effect cannot be restored by Yordam.

Checkpoint UI lists coverage per subject. It does not reduce coverage to one misleading global boolean.

### 8.3 Eligibility

A checkpoint is selectable only at a durable boundary with no unresolved permission, executing tool, incomplete transaction, or unmatched activity. A failed checkpoint is visible as a diagnostic but cannot be used for rewind.

## 9. Fork and Rewind

### 9.1 Context Rewind

`/rewind` defaults to context rewind by fork:

1. user selects a ready checkpoint;
2. Yordam shows omitted turns, current workspace drift, inherited state, reset trust state, and external-effect warnings;
3. user confirms;
4. Yordam atomically creates a new session with parent session, committed parent cursor, checkpoint digest, and trust-reset manifest;
5. the initial child batch terminalizes inherited in-progress work as historical interruption and establishes an idle child state; no inherited plan is actionable;
6. child projection composes the immutable parent prefix through the selected checkpoint and child-local events;
7. mode defaults to `ask`;
8. session grants, broad shell trust, pending approvals, and transient MCP authorization do not transfer;
9. current workspace remains unchanged;
10. source session remains unchanged and available for new independent history, while the child's referenced parent prefix remains immutable.

A fork from a validated prefix of a read-only corrupted session is labeled `salvage fork`.

### 9.2 Fork Failure

- If child creation fails, the user remains on the source session.
- If child creation succeeds but activation fails, the source remains active and the new session ID is displayed for recovery.
- If an executing process cannot be confirmed stopped, fork and rewind remain blocked until the effect is terminalized or explicitly abandoned as uncertain.

## 10. Exact Built-In Edit Restore

### 10.1 Restore Eligibility

Restore is enabled only when:

- the effect came from Yordam's built-in edit tool;
- complete preimage existence state, bytes, supported permission bits, and digests were durably captured in the confidential recovery store;
- the corresponding postimage and terminal file-change evidence are known;
- no path is missing from the requested restore set;
- the current subject is a supported regular file or a built-in-created regular file and can be safely opened and verified;
- no unknown or non-built-in mutation breaks the post-checkpoint edit chain for that path.

Diff text alone is not sufficient restore material. Exact restore covers file existence, bytes, and supported permission bits. It does not promise ownership, ACL, extended-attribute, hard-link, symlink, directory, device, or arbitrary metadata restoration. A built-in-created regular file may be removed only when its current digest still matches the captured final postimage.

For repeated built-in edits to one path after the selected checkpoint, Yordam validates a contiguous hash chain. The desired restored state is the preimage of the earliest eligible post-checkpoint edit. A chain gap disables exact restore for that path.

### 10.2 Restore Flow

1. Compute the desired state from the selected checkpoint and eligible contiguous edit chains.
2. Atomically create the child fork and activate it in a blocked `restore_preparing` recovery state before any workspace write. The source remains immutable history and normal task execution is blocked.
3. Compute exact inverse changes and durably commit the canonical per-path restore plan, purpose, resources, and plan digest.
4. Create confidential recovery coverage and a pre-restore checkpoint bound to that exact digest.
5. Display the inverse changes and collect homogeneous or per-path R3/R4 user responses; heterogeneous paths never receive one bulk approval. Responses remain provisional until final validation.
6. Preflight every path and confirm the plan digest after all responses.
7. If preflight finds drift, commit no effective authorization, write nothing, and terminalize the child as `restore_not_applied` with reason `drifted`.
8. Commit effective authorization and atomically consume once-decisions with the restore activity start.
9. Immediately before each replacement, re-resolve and revalidate that path. Commit `write_attempted` for that path before invoking replacement, then apply through the hardened atomic file operation and record its result immediately.
10. Run every mutation-capable post-action, verification, and turn-complete command hook before the final verifier suite.
11. Verify restored subjects and issue a `RestoreReceipt` listing restored, unchanged, drifted, failed, unknown, and external subjects.
12. On complete success, transition the child to idle. On any possible post-write failure, transition it to `recovery_required`; normal turns remain blocked until explicit reconciliation.

Proven no-write exits are deterministic: denial, cancellation, checkpoint failure, preflight drift, or crash before the durable first `write_attempted` event terminalize the child as `restore_not_applied`; the child becomes an idle context-only fork with current-workspace drift warnings, and the user may return to the source session. Once `write_attempted` is durable or effect cannot be disproved, every exit is `recovery_required`.

### 10.3 Partial Failure

Yordam does not promise general multi-file filesystem atomicity on macOS or Linux. Drift found during complete preflight produces zero writes. A concurrent change, crash, or filesystem error after the first replacement may produce a partial restore. Yordam records each confirmed path, marks the child `recovery_required`, never retries automatically, and never reports success.

### 10.4 Unsupported Effects

Yordam does not restore:

- arbitrary shell filesystem changes;
- network operations;
- spawned process state;
- command-hook effects;
- arbitrary local MCP process effects;
- remote MCP or remote API changes.

Observed Git or filesystem differences may be evidence, but do not become restore guarantees.

## 11. Receipt Model

Receipt types are distinct:

- `ActivityReceipt`: one execution or remote observation and its evidence;
- `VerificationReceipt`: one bounded verifier assertion;
- `RestoreReceipt`: per-subject restore outcomes and coverage;
- `TaskReceipt`: outcome-contract and criterion aggregation;
- `RunReceipt`: the single headless terminal envelope that references the applicable task, activity, verification, restore, permission, auth, configuration, or storage receipts.

Receipts share canonical identity, subject references, evidence links, environment, coverage dimensions, and canonical integrity checksum fields. A digest is an integrity checksum, not proof against an attacker who can rewrite both data and checksum.

### 11.1 Receipt Content

A `VerificationReceipt` contains:

- receipt identity and digest;
- task, contract version, criterion, activity, and subject references;
- verifier identity and version;
- requested and effective execution profile;
- environment description;
- start and terminal time;
- command or structured verification method;
- exit status and diagnostics;
- input and output evidence;
- verified, failed, or unknown status;
- coverage statement and unsupported conclusions.

### 11.2 Honest Claims

Examples of acceptable receipt claims:

- command exited zero in the stated local profile;
- file digest equals the expected digest;
- test runner output reports 100 successful iterations;
- race detector completed with exit zero;
- structured output conforms to the declared schema.

Examples of prohibited overclaims:

- implementation is correct;
- there are no races anywhere;
- remote system state is permanently updated;
- shell had no effects outside the observed Git diff.

### 11.3 Outcome Integration

Criterion assessment links one or more `VerificationReceipt` values and explains the mapping from evidence to criterion. Waiver is a user decision stored in the `TaskReceipt`, not verifier output. Missing or stale evidence leaves the criterion `unknown`, not verified.

## 12. Context, Usage, and Cost Visibility

The context planner records:

- model context window when known;
- estimated input tokens before request;
- output reserve;
- included sources and their provenance;
- excluded sources and reasons;
- active compaction summary;
- contract, instruction, skill, message, tool, and evidence contributions.

Provider usage records distinguish:

- input tokens;
- output tokens;
- cached input/write tokens where available;
- reasoning tokens where reported;
- actual versus estimated usage;
- interrupted attempt with unknown terminal usage.

Cost records include currency, pricing source, pricing version or date, and `calculated`, `actual_billed`, or `unknown` status. Locally multiplying provider-reported usage by configured pricing is `calculated`; `actual_billed` requires provider billing evidence. Unknown pricing never displays as zero cost.

## 13. Accessibility and Terminal Behavior

- keyboard-only operation is complete;
- color is never the sole status or risk signal;
- focus indicators and text markers remain visible with `NO_COLOR`;
- reduced-motion/plain mode replaces spinners and incremental repaint with stable state updates;
- a non-alternate-screen transcript mode is available;
- control characters in provider and tool strings are escaped;
- wide and combining characters use display-width-aware layout;
- resize preserves draft, focus, stream position, inspector selection, and permission queue position;
- deny and cancel remain reachable when the terminal is too small to show approval evidence safely;
- security-critical text wraps or scrolls instead of truncating.

The supported interactive minimum is 60 columns by 16 rows. Below either dimension, Yordam renders a stable terminal-too-small surface; deny, cancel, and quit remain available, while approval is disabled until critical evidence can be displayed safely.

## 14. System States and Errors

| State | UI and System Behavior |
|---|---|
| Configuration blocked | Draft remains; no task mutation or provider request begins |
| Contract proposed | Criteria visible; mutations blocked until freeze |
| Permission pending | Blocking surface shows queue position and exact axes |
| Decision stale | No execution; card shows changed plan or scope and requests re-evaluation |
| Checkpoint failed | Mutation does not start; checkpoint remains non-selectable |
| Context fork ready | Source remains available; workspace unchanged |
| Restore not applied | Proven pre-write denial, cancellation, checkpoint failure, or drift; no `write_attempted` exists and the context-only child is idle |
| Restore recovery required | A `write_attempted` exists or effect cannot be disproved; confirmed paths and uncertainty shown, normal child turns blocked, no automatic retry |
| Verification unknown | Task cannot become verified solely from assistant text |
| Recovered with uncertain effect | Warning persists until inspected; no automatic continuation |
| Read-only corruption | Validated prefix visible; only inspection and salvage fork available |

## 15. Acceptance Criteria

### Outcome

- [ ] Given a goal without criteria, when the agent proposes criteria, then each criterion names an observable verification method before mutation.
- [ ] Given a frozen contract, when the agent proposes weaker success conditions, then the active contract does not change without an explicit amendment decision.
- [ ] Given a completed model turn without sufficient evidence, when assessed, then the task is `partial` or `unknown`, not `verified`.
- [ ] Given a user waiver, when the final receipt is created, then the waiver remains distinct from verified evidence.
- [ ] Given all required criteria waived, when assessed, then the task is `completed_with_waivers` and excluded from verified-completion metrics.
- [ ] Given missing initial criteria in headless mode, when run, then it exits contract-required without entering a mutation-capable provider phase.

### Cockpit

- [ ] Given a consequential activity, when rendered, then Purpose, Evidence, Decision, and Verification are separately labeled.
- [ ] Given agent purpose text, when rendered, then it is labeled as a claim rather than proof.
- [ ] Given a 120-column terminal, when the cockpit renders, then ledger and inspector are simultaneously usable.
- [ ] Given a terminal below 120 columns, when the inspector opens, then it replaces the stream and restores draft, scroll, and focus when closed.
- [ ] Given critical risk text, when space is constrained, then it remains inspectable without semantic truncation.
- [ ] Given any cockpit state, when inspected, then no raw chain-of-thought field exists.

### Permission

- [ ] Given multiple model tool intents, when prepared, then only the first unresolved canonical request is actionable and execution remains sequential.
- [ ] Given a permission surface closed with `Esc`, when resolved, then the request is durably denied rather than hidden.
- [ ] Given turn cancellation, when pending requests exist, then each becomes cancelled, not user-denied.
- [ ] Given a duplicated allow-once decision nonce, when two dispatches race, then exactly one activity can start.
- [ ] Given an exact session grant, when listed, then its true future capability and scope are visible and revocable.
- [ ] Given broad shell trust, when enabled, then it uses a separate confirmation, remains visible, and is revoked on applicable mode exit or fork.
- [ ] Given a changed plan digest or scope, when execution is attempted, then no side effect starts.

### Checkpoint and Rewind

- [ ] Given a planned mutation, when checkpoint creation fails, then the mutation does not start.
- [ ] Given context rewind, when completed, then the source session journal is byte-for-byte unchanged.
- [ ] Given a mid-turn checkpoint, when forked, then the child bootstrap marks inherited work historical and starts idle with no actionable inherited plan.
- [ ] Given a context-only fork, when activated, then workspace files are unchanged and trust-sensitive session state is reset.
- [ ] Given a corrupted source with a validated prefix, when salvage fork is selected, then the source remains read-only and unchanged.
- [ ] Given an active or uncertain process effect, when rewind is requested, then rewind remains blocked until its state is explicitly resolved or abandoned as uncertain.

### Restore

- [ ] Given complete built-in edit material and matching current preimages, when restore is approved, then exact content and permissions are restored and verified.
- [ ] Given drift found during complete preflight, when restore is attempted, then no target file is written.
- [ ] Given concurrent drift after preflight and one completed replacement, when restore continues, then the child enters `recovery_required` with a partial receipt and no retry.
- [ ] Given only a diff or fingerprint without complete preimage bytes, when restore is requested, then restore is unavailable.
- [ ] Given shell or remote MCP effects after a checkpoint, when a restore receipt is issued, then those effects remain `unknown` or `not_reversible`.

### Verification and Usage

- [ ] Given a test command with exit zero, when a receipt is generated, then it claims only the observed command result and parsed evidence.
- [ ] Given missing evidence, when a criterion is assessed, then it remains unknown.
- [ ] Given provider-reported usage, when displayed, then it is labeled actual and retains attempt identity.
- [ ] Given estimated usage or cost, when displayed, then pricing and estimation provenance are visible.
- [ ] Given unknown pricing, when displayed, then cost is unknown rather than zero.
- [ ] Given locally calculated cost without billing evidence, when displayed, then it is `calculated`, not `actual_billed`.

### Accessibility and Recovery

- [ ] Golden layouts pass at 60, 80, 119, 120, and 160 columns at 16 and 24 rows, plus the terminal-too-small surface below 60x16.
- [ ] Permission, recovery, and restore flows remain operable without color or animation.
- [ ] PTY tests prove resize preservation, permission denial, turn cancellation, checkpoint/fork confirmation, plain mode, and clean terminal restoration.

## 16. Gate Exit

Trust Loop exits only when:

- Foundation acceptance remains green;
- built-in tools use the complete outcome, activity, evidence, permission, checkpoint, restore, and receipt flow;
- a representative 10 to 20 local-task pilot can calculate the PRD metrics without automatic telemetry;
- all uncertainty and unsupported restore paths remain visible and cannot produce `verified` outcomes;
- the Gate 2 evidence records one exact source commit.
