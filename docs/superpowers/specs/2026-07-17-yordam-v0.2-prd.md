# PRD: Yordam v0.2 Trusted Extensibility

Status: approved product design
Date: 2026-07-17
Target release: `v0.2.0`
Primary persona: solo power-user developer
Delivery policy: scope and quality are fixed; schedule is flexible

## 1. Overview

Yordam v0.2 turns a terminal conversation into a verifiable task. A user can define a goal and completion criteria, observe every consequential action through an evidence-linked activity ledger, control permissions using exact scopes, recover through immutable session forks, and verify what actually happened through receipts.

The same trust model applies to built-in tools, native model providers, MCP servers, project agents, instructions, skills, hooks, and headless execution. Extensibility is not treated as a separate plugin feature: every extension must remain inspectable, permissioned, recoverable where technically possible, and explicit about effects Yordam cannot confine or reverse.

## 2. Product Thesis

The best agentic interface minimizes uncertainty at every moment. Yordam must answer:

1. What is the task goal?
2. What is happening now?
3. What user-visible purpose does this step serve?
4. What evidence was observed?
5. What changed and under which permission?
6. What was verified, what remains unknown, and how can the user recover?

Conversation remains an input and explanation surface. The task, its outcome contract, activities, evidence, decisions, checkpoints, and verification state are the primary product objects.

## 3. Background

Yordam v0.1 already provides a strong local trust foundation:

- workspace-scoped durable sessions;
- `safe`, `ask`, and `auto` permission modes;
- prepared edit previews and exact diffs;
- stale-preimage protection;
- durable tool, permission, file-change, and turn lifecycle events;
- cancellation, truncated-tail recovery, and secret redaction;
- immutable runtime selection for an active turn during configuration changes.

The limitations that v0.2 addresses are structural:

- the agent loop is concentrated in one large turn runner;
- model events do not represent capabilities, usage, cost, or provider-specific terminal reasons;
- activity identity and evidence relationships are implicit;
- session rewind, fork lineage, and verification receipts do not exist;
- the TUI shows conversation, a coarse progress state, and a contextual modal rather than an operator ledger;
- provider routing compresses all profiles into one OpenAI-compatible contract;
- the tool registry and permission classification are built-in-specific;
- shell execution is trusted local execution, not an operating-system sandbox.

MCP, subagents, provider portability, permissions, checkpoints, and session continuation are broadly available in competing terminal agents. Yordam will not differentiate by checking those boxes. It will differentiate by making one agent's work understandable, controllable, evidence-linked, and honest about its limits.

## 4. Users

### 4.1 Primary: Solo Power-User Developer

The primary user works in local repositories, is comfortable in a terminal, and already uses a separate editor. They want substantial agent autonomy but do not accept hidden mutations, unverifiable completion claims, or ambiguous recovery.

Primary needs:

- express a task in outcomes rather than only a prompt;
- understand current agent state without reading debug logs;
- approve fewer but more meaningful actions;
- inspect exact scopes, diffs, commands, evidence, and verification;
- recover without destroying the original session;
- use multiple providers and extensions without weakening the trust model;
- automate safely through a fail-closed headless interface.

### 4.2 Secondary: Extension Author

An extension author builds MCP servers, agent definitions, skills, or hooks. They need versioned contracts, deterministic discovery and trust behavior, visible provenance, structured errors, and conformance tests.

### 4.3 Non-Target for v0.2

Team administrators, fleet operators, and multi-agent supervisors are not primary users for this release. Team synchronization, RBAC, central policy, remote runners, and agent fabrics remain future work.

## 5. Goals

Yordam v0.2 must:

1. represent a task as a goal plus a versioned outcome contract;
2. separate model completion from verified outcome completion;
3. project durable execution into an evidence-linked activity ledger;
4. present Purpose, Evidence, Decision, and Verification separately for every consequential action;
5. create automatic checkpoints before mutations;
6. rewind context by creating an immutable session fork;
7. restore only exact built-in edit effects for which complete preimages were captured;
8. issue verification receipts that state both coverage and unknown effects;
9. expose context budget, provider-reported usage, estimates, and cost provenance;
10. support native OpenAI, Anthropic, and Gemini adapters while retaining the OpenAI-compatible adapter;
11. negotiate provider capabilities and reject unsupported required behavior without silent emulation;
12. support MCP tools, resources, and prompts over local stdio and remote Streamable HTTP;
13. support environment-referenced bearer credentials and MCP-compliant OAuth 2.1 for remote servers;
14. keep MCP authentication separate from Yordam action authorization;
15. load user and explicitly trusted project agents, instructions, skills, MCP definitions, and hooks with visible provenance;
16. support declarative hooks and trusted command hooks under the same permission and execution model;
17. provide a versioned, one-way headless JSONL event stream with deterministic exit codes and final receipts;
18. preserve v0.1 session readability and all v0.1 security and recovery guarantees;
19. retain a local control plane, local persistence, and automatic-telemetry-free defaults; configured provider and MCP actions remain explicit network operations.

## 6. Success Metrics

### 6.1 North Star

`Verified task completions per human intervention`

Definitions:

- A verified task completion has every required criterion assessed as verified using runtime or tool evidence. Assistant text alone is not verification.
- A human intervention is a correction, retry instruction, outcome-contract amendment, or manual recovery action after task execution begins.
- Permission decisions are measured separately and are not counted as corrections. This prevents pressure to bypass meaningful approvals.

### 6.2 Input Metrics

| Metric | Definition | Decision Supported |
|---|---|---|
| Verified completion rate | Verified tasks divided by terminal tasks | Whether the trust loop produces evidence-backed outcomes |
| Interventions per verified task | Corrections, retries, amendments, and manual recoveries per verified task | Whether autonomy is useful rather than merely active |
| Approvals per task by risk class | Human permission decisions grouped by effect class | Whether permission UX is precise without becoming noisy |
| Receipt coverage | Consequential terminal activities with complete verification coverage metadata | Whether completion claims are auditable |
| Successful restore rate | Exact restore attempts completed and post-verified | Whether rewind promises are reliable |
| State-understanding time | Time for a pilot user to answer goal/current action/risk/next recovery | Whether the cockpit reduces uncertainty |
| Uncertain effect rate | Tasks containing effects classified as unknown or externally unverifiable | Whether unsupported guarantees are visible |

### 6.3 Guardrails

- zero side effects before a durable authorization decision;
- zero automatically repeated unmatched mutations after recovery;
- zero false `verified` outcomes based only on model claims;
- zero registered secret byte sequences in events, ordinary evidence, logs, receipts, TUI output, or headless output; confidential exact-restore material is separately protected and never model-visible or normally exportable;
- zero silent provider capability emulation;
- zero project executable activation before explicit workspace trust;
- zero source-session truncation or mutation during rewind;
- zero automatic headless approval when the effective decision is `ask`.

### 6.4 Baseline Policy

No credible behavioral baseline exists in v0.1 because tasks, interventions, criteria, and receipts are not first-class objects. v0.2 first instruments the definitions above locally. Quantitative product targets are set after a representative pilot of 10 to 20 local tasks. Release acceptance uses deterministic technical gates rather than invented behavioral targets.

Yordam sends no automatic telemetry. Metrics are calculated locally from the ledger. The user may explicitly export a human-readable metric report.

## 7. Scope

### 7.1 In Scope

#### Trust Loop

- goals and outcome contracts;
- completion-criteria drafting, freezing, explicit amendment, and assessment;
- activity ledger and operator cockpit;
- risk-aware permission queue and grant revocation;
- automatic checkpoints;
- context rewind through immutable session forks;
- exact built-in edit restore with stale-preimage checks;
- verification receipts;
- context, token, usage, and cost visibility;
- `restricted local` and `trusted local` execution-policy profiles.

#### Extensibility

- native OpenAI, Anthropic, and Gemini adapters;
- retained OpenAI-compatible adapter;
- provider capability negotiation and normalized usage;
- MCP tools, resources, and prompts;
- MCP stdio and Streamable HTTP transports;
- bearer secret references and OAuth 2.1 authorization;
- user and project agent definitions;
- user and project instructions and skills;
- declarative and command hooks;
- explicit workspace trust and executable-digest re-approval;
- versioned headless JSONL events and receipts.

#### Foundation and Release

- versioned event and application protocols;
- typed event payloads and activity identity;
- event-journal and evidence-store evolution;
- v0.1 event upcasting;
- crash-boundary recovery and adversarial security testing;
- provider and MCP conformance suites;
- macOS and Linux release evidence for amd64 and arm64.

### 7.2 Non-Goals

- subagents, agent trees, or agent-to-agent communication;
- parallel agent or parallel tool execution;
- task dependency graphs;
- steering queues or pausing individual workers;
- remote runners, session attach, or daemon/client separation;
- operating-system sandbox guarantees;
- restoring arbitrary shell, network, local-process, or remote-system effects;
- extension marketplace, installer, package registry, or automatic discovery outside configured sources;
- repository-owned executable activation without explicit workspace trust;
- team synchronization, shared policy registry, SSO, RBAC, or organization audit retention;
- desktop application, integrated code editor, or permanent IDE layout;
- raw chain-of-thought, hidden scratchpad, or reasoning-token content display;
- cloud account requirements or automatic telemetry.

## 8. Product Principles

1. **Evidence before claims.** Model text may describe intent or conclusions but cannot verify itself.
2. **Task before conversation.** Conversation supports the task; it is not the execution model.
3. **Durability before side effects.** Required intent and authorization records are durable before execution.
4. **Immutable recovery.** Rewind creates a fork and never destroys the source history.
5. **Exact promises only.** Yordam reports actual enforcement and restore coverage, not aspirational isolation.
6. **Authentication is not authorization.** Provider or MCP credentials do not authorize an action's effect.
7. **Capabilities are negotiated.** Unsupported required behavior fails visibly instead of being silently approximated.
8. **Extensions inherit the core trust model.** MCP, hooks, skills, and providers do not bypass evidence, policy, or recovery boundaries.
9. **Project content is untrusted until approved.** Discovery does not imply activation.
10. **Local first.** Sessions, metrics, credentials, and control remain local unless the user explicitly invokes a configured remote service.

## 9. Release Contract

`v0.2.0` is one release with four internal acceptance gates:

1. Protocol Foundation
2. Trust Loop
3. Extensibility
4. Release Proof

Each gate produces acceptance evidence and retains all prior gate suites. No gate is shipped as a preview or independent public version. The release tag is created only after every gate passes.

The approved JSONC configuration and `/reload` design is a prerequisite, not an internal v0.2 gate or part of the v0.2 feature scope. It must be completed and accepted as a clean baseline before Foundation work starts. That baseline rejects durable literal API-key values; credentials use environment or credential-store references.

## 10. Requirements Overview

| ID | Requirement |
|---|---|
| PRD-FR-01 | A task has a goal, a versioned outcome contract, and criterion-level status. |
| PRD-FR-02 | Every consequential action has separate Purpose, Evidence, Decision, and Verification projections. |
| PRD-FR-03 | A mutation cannot start before its checkpoint, execution plan, and effective authorization are durable. |
| PRD-FR-04 | Context rewind creates a new session fork and preserves the source session unchanged. |
| PRD-FR-05 | Workspace restore is available only for exact built-in edit material and revalidates current preimages. |
| PRD-FR-06 | Provider adapters publish capabilities, context limits, usage support, and terminal reasons. |
| PRD-FR-07 | Required unsupported provider capabilities fail visibly without silent emulation. |
| PRD-FR-08 | MCP authentication and each MCP action's Yordam authorization are evaluated separately. |
| PRD-FR-09 | Project agents, instructions, skills, MCP definitions, and hooks require explicit workspace trust before activation. |
| PRD-FR-10 | Headless execution fails closed when an action requires interactive approval. |
| PRD-FR-11 | v0.1 sessions remain readable without inventing v0.2 evidence or guarantees. |
| PRD-FR-12 | All metrics remain local unless the user explicitly exports a report. |

## 11. Dependencies and Constraints

| Item | Type | Impact |
|---|---|---|
| Approved JSONC and `/reload` implementation | Prerequisite | Provides atomic runtime-generation replacement and configuration schema baseline |
| Existing append-only session store | Architecture | Must evolve without invalidating readable v0.1 sessions |
| Single-process, single-active-turn model | Product and architecture | Preserved in v0.2; reduces concurrency and recovery ambiguity |
| macOS and Linux support | Platform | OAuth credential storage and process behavior require both platform paths |
| Provider APIs | External | Native semantics and usage availability differ; the UI must show unknown values honestly |
| MCP specification | External protocol | Transport, lifecycle, tool/resource/prompt, and OAuth behavior require conformance tests |
| No OS sandbox | Trust boundary | Execution profiles describe policy and effective behavior, not process confinement |

## 12. Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| The merged scope becomes an unreviewable monolith | High | Foundation-first gates and separate implementation plans per gate |
| Event migration corrupts or misrepresents old sessions | Critical | Versioned codecs, deterministic upcasting, fixtures, read-only failure mode |
| "Checkpoint" is interpreted as universal undo | Critical | Separate context fork, exact edit restore, drift detection, and external-effect classifications |
| MCP annotations cause unsafe automatic permission decisions | Critical | Treat annotations as untrusted hints; derive Yordam risk independently |
| OAuth tokens leak through logs or artifacts | Critical | OS credential store, secret references, redaction, synthetic-secret acceptance scans |
| Provider abstraction erases native behavior | High | Provider-neutral content blocks plus explicit capability negotiation and no silent emulation |
| Permission UX creates excessive prompts | Medium | Policy-resolve low-risk calls; measure approvals by risk class; expose exact session capability semantics |
| Evidence volume degrades session performance | High | Range reads, projections, per-session locking, expected-head append, content-addressed blobs |
| Hooks introduce recursion or bypass policy | Critical | Typed phases, recursion guards, timeouts, execution-policy integration, durable invocation receipts |

## 13. Rollout

1. Complete the JSONC and `/reload` prerequisite and refresh the v0.1 acceptance baseline.
2. Implement and accept Protocol Foundation without changing the public product promise.
3. Enable Trust Loop flows for built-in tools and validate them through local pilot tasks.
4. Add Extensibility surfaces behind the same stable application, event, evidence, and authorization contracts.
5. Run complete migration, adversarial, conformance, PTY, and release acceptance.
6. Publish `v0.2.0` only when every internal gate passes on one exact release-candidate commit.
