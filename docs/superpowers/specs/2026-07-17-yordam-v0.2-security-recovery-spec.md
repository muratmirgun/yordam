# Feature Spec: Yordam v0.2 Security and Recovery

Status: approved design
Date: 2026-07-17
Parent PRD: [Yordam v0.2 Trusted Extensibility](2026-07-17-yordam-v0.2-prd.md)
Normative contract: [Yordam v0.2 Capability Contract](2026-07-17-yordam-v0.2-capability-contract.md)
Applies to: all v0.2 gates

## 1. Purpose

This specification defines the trust boundaries, secret handling, policy precedence, durable ordering, crash recovery, corruption behavior, and uncertainty semantics that apply to every v0.2 feature.

Yordam's security promise is precise rather than absolute. It provides canonical path authorization for built-in file tools, structured action authorization, durable decisions, bounded evidence, secret redaction, explicit project trust, and deterministic recovery. It does not claim operating-system confinement for local processes or reversal of arbitrary external effects.

## 2. Threat Model

### 2.1 Protected Assets

- files inside and outside the workspace;
- session journals, task history, evidence, checkpoints, and receipts;
- provider and MCP credentials;
- OAuth access and refresh tokens;
- environment variables and local process privileges;
- model context and project instructions;
- remote-system state reachable through MCP or network-capable processes;
- terminal integrity and user decision accuracy.

### 2.2 Untrusted Inputs

- user prompts and pasted content;
- model output and tool arguments;
- repository contents and project configuration;
- MCP server descriptors, annotations, instructions, tools, resources, prompts, results, logs, and redirects;
- provider responses, errors, usage metadata, and request identifiers;
- hook output and diagnostics;
- event journals or artifacts modified outside Yordam;
- filesystem paths, symlinks, race conditions, and concurrent writers;
- shell and process output containing control characters or secrets.

### 2.3 Trusted Components

Trust is scoped, not universal:

- Yordam's signed or locally built binary is trusted to enforce this specification;
- user configuration is trusted after local parsing and validation;
- project configuration is inactive until explicit workspace trust;
- a configured provider or MCP server is trusted only for the capabilities and data the user intentionally exposes;
- MCP annotations and returned instructions are content, not policy authority;
- local executables remain capable of acting with user privileges even when their invocation was authorized for a narrow purpose.

### 2.4 Primary Threats

- unauthorized or stale-scope file mutation;
- path escape through symlink or time-of-check/time-of-use races;
- permission decision reuse against changed plans;
- prompt injection from project or MCP content that attempts to override policy;
- secret leakage through config, environment, diagnostics, evidence, or model context;
- OAuth token substitution, audience confusion, redirect abuse, or token passthrough;
- malicious or malformed MCP and hook processes;
- false verification or overstated restore coverage;
- automatic replay of an interrupted mutation;
- journal corruption, partial transactions, and concurrent-writer ambiguity;
- terminal escape injection and unreadable critical permission text;
- unbounded output, event queues, retries, or process lifetimes.

## 3. Execution Boundary

### 3.1 Built-In File Tools

Built-in read, search, and edit tools retain canonical path and rooted file-operation defenses. Authorization occurs against structured canonical resources. Immediately before execution, the tool re-resolves and revalidates the target through the hardened filesystem path.

For edit:

- complete restore material is captured before mutation when exact restore is promised;
- the planned preimage digest is verified immediately before write;
- the write uses the hardened atomic replacement path;
- postimage digest and file metadata are recorded;
- automatic retry after an attempted write is prohibited.

### 3.2 Local Processes

Shell, command hooks, executable verifiers, and stdio MCP servers are local processes with the user's operating-system privileges unless a future sandbox backend explicitly says otherwise.

Yordam may restrict:

- whether a process may start;
- executable, arguments, and working directory;
- environment allowlist;
- timeout and process-group lifetime;
- model-visible and retained output bounds;
- permission and evidence requirements.

Yordam v0.2 does not enforce general filesystem, network, syscall, or child-process confinement. `restricted local` is a policy profile, not an OS sandbox.

### 3.3 Remote Effects

Remote MCP and provider calls occur outside Yordam's local process boundary. Yordam can control whether it sends a request, what authenticated resource receives it, and what evidence it records. It cannot guarantee the remote implementation's internal behavior, data retention, or reversibility.

Remote receipts use separate typed dimensions: observation source (`local_observed`, `provider_reported`, `server_reported`, or `unknown`), verification coverage (`exact`, `partial`, `response_only`, or `unknown`), and reversibility (`exact`, `detectable_only`, `unknown`, or `not_reversible`). Outcome status remains a separate field. They do not claim universal state restoration.

## 4. Authorization Security

### 4.1 Structured Scope

Authorization scope uses typed resource references rather than display strings. Examples include:

- canonical local file;
- canonical search root;
- command plus working directory and effective environment class;
- canonical MCP server and tool identity;
- canonical MCP resource URI;
- remote target or resource key declared by an adapter;
- hook identity and phase;
- credential binding reference.

Human-readable summaries derive from structured scope. They are not used as authorization keys.

### 4.2 Decision Binding

An allow decision binds to:

- canonical principal;
- session or control-operation identity;
- task and turn identity when present;
- activity and call or queue identity;
- canonical tool or hook identity and source;
- source revision and descriptor digest;
- action type;
- structured resource set;
- execution-plan digest;
- runtime generation;
- policy generation;
- decision nonce;
- lifetime and expiry conditions.

Any relevant change invalidates the decision. Invalid or stale approval responses are durably denied and execute nothing. A once-decision is consumed atomically with the matching activity-start commit. Session grants are explicitly session-bound and cannot cross forks or sessions.

### 4.3 Policy Precedence

The effective decision uses a monotonic constraint lattice:

1. unsupported or impossible platform guarantee and hard deny are terminal;
2. user policy establishes the maximum capability set;
3. trusted project policy intersects and may only narrow that set;
4. ordinary deny is terminal;
5. an active session grant may resolve only an effective `ask` within all constraints;
6. an interactive response may resolve only the remaining `ask` and cannot override a deny.

Provider, MCP, agent, skill, instruction, or hook content cannot introduce an allow decision.

### 4.4 Prompt and Content Injection

Instructions from different sources retain provenance and precedence. Untrusted project or MCP content is wrapped or represented as content, never concatenated into a trusted policy layer without source identity.

The system policy explicitly states that tool results, resources, prompts, repository files, and external content may contain instructions but cannot change authorization, secret handling, execution profiles, or outcome-contract rules.

## 5. Project Trust

### 5.1 Before Trust

Before explicit workspace trust, Yordam may parse and summarize project configuration but must not:

- insert project instructions or skills into model context;
- select a project agent;
- launch a project MCP server;
- run a project command hook;
- read a project-declared secret binding;
- apply a project policy;
- contact a project-declared remote endpoint.

### 5.2 Trust Record

The durable trust record contains no secret values. It identifies:

- canonical workspace;
- trusted configuration source files and digests;
- canonical executable launch manifests, resolved source digests, interpreter, arguments, working directory, environment names, and credential-binding identities;
- remote MCP endpoint, transport, canonical resource, and OAuth issuer binding;
- requested environment and credential references;
- effective policy delta;
- user decision time and actor;
- revocation and supersession state.

### 5.3 Revalidation

Trust is re-requested for executable, remote-target, credential-binding, or capability-broadening changes as defined in the Extensibility spec. A workspace-root replacement, symlink swap, canonical-path change, PATH resolution change, interpreter change, script-byte change, or source-revision change invalidates trust. The race-resistant launch adapter hashes source bytes from open handles and executes verified descriptors or private immutable staging copies; it never validates one repository path and later spawns from that re-resolvable path. Final manifest validation, live revocation check, and process registration are linearized under the dispatch lock.

Revocation increments a live hard-deny epoch checked before every dispatch. It prevents future runtime-generation activation, blocks new project-owned activity inside active turns, and terminates project-owned processes where possible. Unconfirmed termination or external effects become uncertain and remain visible.

## 6. Secrets and Credentials

### 6.1 Secret References

Configuration stores secret identifiers or environment-variable names, never raw provider keys, bearer tokens, client secrets, access tokens, or refresh tokens.

The JSONC prerequisite removes literal provider API-key decoding, schema support, template output, and persistence before Foundation begins. A future encrypted secret store requires a separately approved design; v0.2 accepts only environment or credential-store references.

### 6.2 Secret Binding

Secret resolution returns an in-memory binding with:

- secret identity;
- source type;
- allowed consumers;
- creation and expiry metadata;
- redaction registration;
- no string representation that reveals the value.

Bindings are scoped to one runtime generation. Failed candidate generations release bindings promptly.

### 6.3 Child Environments

Local child environments start from an explicit allowlist. They do not inherit the complete Yordam process environment.

At minimum, provider keys, MCP bearer tokens, OAuth tokens, credential-store material, and configured secret values are absent unless the specific child definition explicitly references an allowed secret. Project sources cannot request an undeclared environment pass-through.

### 6.4 OAuth Tokens

- access and refresh tokens use OS credential storage when available;
- process-memory-only fallback is permitted;
- plaintext disk fallback is prohibited;
- token lookup keys do not contain token values;
- refresh follows rotation semantics when a new refresh token is issued;
- known revoked or expired tokens are not sent;
- stored credentials bind the protected-resource metadata URL, canonical resource, authorization-server issuer, client ID, scopes, account identity when available, and runtime generation;
- opaque token contents are not claimed locally audience-inspectable; Yordam enforces its issuance binding and target-resource binding;
- Yordam itself never performs token passthrough as upstream API credentials. It cannot guarantee an independent remote MCP server's downstream implementation.

### 6.5 Redaction

Registered-secret admission scanning and redaction applies before persistence or display to:

- event payloads;
- evidence metadata and blobs where text is retained;
- provider and MCP errors;
- hook stdout/stderr;
- shell stdout/stderr;
- ordinary recovery diagnostics and artifacts, excluding access-restricted confidential restore bytes;
- debug logs;
- TUI and headless output;
- final receipts and metric exports.

Every ordinary text or binary blob is byte-scanned in memory before any durable or temporary write for registered raw byte sequences plus standard Base64, URL-safe Base64, and lowercase/uppercase hexadecimal encodings. On detection, Yordam persists only redacted metadata stating that content was withheld; it does not persist the original bytes. Streaming scanners preserve boundary overlap across chunks. Confidential restore material is scanned in memory before staging; detection disables exact restore and leaves no temporary material.

Secret-aware streaming redaction must handle the same registered variants when split across deltas. Redaction registration includes every active runtime generation's secret values until no consumer can emit buffered output from that generation.

Redaction is defense in depth, not permission to send arbitrary secret-bearing inputs to providers or extensions. Yordam cannot guarantee detection of transformed, encoded outside supported encodings, previously unknown, or independently read secrets emitted by an unsandboxed child. Explicit child-environment allowlists and permission boundaries reduce that exposure.

## 7. OAuth and Remote Transport Security

Remote MCP authorization follows pinned MCP authorization profile `2025-11-25` and these additional requirements:

- HTTPS is required except explicit localhost development endpoints;
- authorization-server and protected-resource metadata fetches enforce URL, redirect, DNS, and private-network policy to reduce SSRF and DNS-rebinding risk;
- browser redirect listeners bind only to loopback and use unpredictable state;
- callback state is single-use, time-bounded, and bound to issuer, client, redirect URI, and canonical resource;
- authorization responses and token endpoints are checked against the discovered issuer to prevent mix-up;
- redirect URI comparison is exact;
- PKCE S256 is mandatory;
- `resource` is included in authorization and token requests;
- access tokens are sent only under the stored local issuance binding to the canonical intended MCP resource;
- authorization headers are never preserved across untrusted redirects;
- request and step-up retry counts are bounded;
- MCP session IDs are treated as secrets for logging and cross-origin handling;
- Streamable HTTP request bodies, SSE events, and reconnect cursors are bounded.

Remote server URLs containing user information or URI fragments are rejected. Configured hostname and resolved-network changes that violate remote policy stop the connection.

## 8. Output, Schema, and Terminal Safety

### 8.1 Bounds

All provider, MCP, hook, tool, and process outputs have:

- per-message or frame limit;
- model-context excerpt limit;
- retained evidence limit;
- total request or process limit;
- timeout;
- explicit truncation metadata.

The existing 32 KiB model excerpt and 10 MiB retained-output defaults remain unless a later implementation plan changes them through a reviewed limit migration. Limits apply before unbounded allocation.

### 8.2 Schema Validation

- model tool arguments are validated before planning;
- MCP input and output schemas are validated when declared;
- hook input and output use fixed schemas;
- application and headless protocol payloads are validated;
- event payload validation is kind- and version-specific;
- unknown fields follow each protocol's compatibility rules rather than a global permissive default.

### 8.3 Terminal Escaping

Untrusted strings are normalized for terminal display. Control characters and terminal escape sequences are escaped or stripped according to context. Exact binary or control-bearing evidence remains available only through safe artifact inspection, not direct terminal execution.

## 9. Durable Ordering and Crash Points

### 9.1 Mandatory Barriers

For contract drafting, durable goal/draft and provider-egress authorization precede the request, and observation results are durable before provider continuation. For each later consequential action:

1. frozen contract is durable before mutation-capable provider behavior;
2. canonical activity plan, purpose, resources, and plan digest are durable;
3. required checkpoint and confidential restore material referencing that digest are durable;
4. final resource validation confirms the same plan digest;
5. effective permission is durable;
6. the once-decision is atomically consumed with `activity.started`;
7. action may begin;
8. terminal action state and evidence are durable;
9. result may return to the provider;
10. verification and criterion assessments are durable;
11. terminal turn and task state are durable.

A plan or resource change after checkpointing invalidates both checkpoint coverage and authorization and returns to planning.

### 9.2 Process Kill Recovery

Fault-injection tests kill the process immediately before and after every mandatory barrier. Recovery must identify the last committed state and never infer that an action did or did not occur without evidence.

An unmatched start results in:

- `interrupted_no_effect` when the runtime can prove no effect began or the process was cancelled before effect;
- `uncertain` when effect may have occurred;
- observed file-state comparison for built-in edits;
- no automatic execution retry.

## 10. Journal Integrity and Corruption

### 10.1 Envelope and Sequence

The journal validates envelope version, required identity, local sequence, timestamp, kind, payload version, payload schema, and transaction state.

### 10.2 Integrity Checksums

v0.2 uses mandatory canonical encoding and records:

- evidence blob digests;
- receipt digest over canonical receipt fields and evidence references;
- checkpoint state and restore-material digests;
- optional per-event previous-hash chain when implementation review confirms a useful local-corruption diagnostic.

These are integrity checksums for accidental corruption and broken references, not adversarial authenticity. An attacker able to rewrite a locally stored record and checksum can recompute them; even a local hash chain has no external trust anchor. Digital signing and adversarial tamper evidence are not part of v0.2.

### 10.3 Corruption Behavior

- incomplete final fragments are preserved outside the canonical journal;
- invalid data before the final fragment stops writable replay at the validated prefix;
- source data remains unchanged except through an explicit, evidence-producing recovery operation;
- read-only sessions allow inspection and validated-prefix salvage fork;
- projections never skip invalid known events and continue as if nothing happened.
- unknown event kinds or unsupported payload versions make the validated prefix read-only unless an explicitly understood projection-domain marker declares them safely skippable.

Incomplete-tail recovery preserves the original with digest, writes and synchronizes a temporary valid-prefix journal, updates rebuildable metadata, atomically activates the recovered journal, and synchronizes the parent directory. Disk-full, fsync, rename, and process-death failures at each step leave an identifiable original or candidate rather than silent data loss.

### 10.4 Concurrent Writers

The session repository prevents ambiguous concurrent writes through expected-head checks and cross-process exclusion. If cross-process exclusion cannot be established, the session opens read-only rather than relying on process-local locks.

## 11. Checkpoint and Restore Security

### 11.1 Restore Material

Exact edit restore material lives in the confidential recovery-material store and contains:

- canonical path identity at capture time;
- complete preimage content;
- preimage digest;
- expected postimage digest;
- file permissions and required metadata;
- producing activity and checkpoint;
- sensitivity classification;
- access-restricted material reference separate from ordinary evidence.

Restore material is never model-visible, rendered, or normally exported. It uses mode `0600` under a mode `0700` data path and platform-backed encryption when available. If secure retention cannot be provided or registered secret bytes are detected, exact restore is disabled for that subject and only digest-based drift detection remains.

### 11.2 Restore Authorization

Restore is a new mutation evaluated under current policy and current path boundaries. Prior permission for the original edit does not authorize restore.

### 11.3 Drift and Partial State

If complete preflight finds current state differs from the expected post-edit state, restore stops before writing. Each path is re-resolved and revalidated again immediately before its replacement. A concurrent change after preflight may cause a partial restore and is recorded honestly. A user must resolve drift through a new task or explicit manual action; v0.2 has no force-restore option.

Partial restore cannot be called successful. Its receipt lists each confirmed, failed, untouched, and uncertain subject.

## 12. Cancellation and Cleanup

- provider, MCP, hook, shell, verifier, and storage operations accept cancellation;
- local processes use process groups where supported;
- cancellation sends graceful termination, waits a bounded interval, then force-kills;
- remote MCP cancellation follows the negotiated MCP mechanism where possible;
- network disconnection alone is not treated as proof of cancellation;
- cleanup uncertainty remains visible and blocks rewind when effects may still be active;
- TUI terminal restoration executes on normal exit, cancellation, application error, and supported signals.

## 13. Verification Security

### 13.1 Verifier Independence

An executable verifier uses the ordinary R5 execution planner, authorization, checkpoint rule, environment allowlist, process group, output bounds, and uncertainty handling. It remains a distinct activity with explicit inputs and receipts. A denied verifier starts no process or network activity. Mutations produced by a verifier remain consequential activities and cannot be hidden behind a successful receipt. The model that proposed a change cannot verify it solely by restating success.

### 13.2 Receipt Integrity

Receipts use canonical encoding and reference immutable evidence digests and the effective environment. A missing, changed, or unavailable evidence blob invalidates the corresponding verified status on replay. Receipt checksums do not claim signer identity or attacker-resistant authenticity.

### 13.3 Scope of Claims

Receipts use bounded claims. Exit zero, parsed test output, digest equality, and schema validity are observations. Broader correctness, absence of all races, and reversal of remote state are not inferred.

## 14. Recovery States

| State | Meaning | Allowed Actions |
|---|---|---|
| Ready | Writable journal and no unresolved recovery | Normal task operations |
| Recovered writable | Incomplete tail safely isolated; committed history valid | Inspect and start new turn |
| Effect uncertain | Started activity may have affected state | Inspect, explicitly abandon, or manually reconcile; no automatic retry |
| Interrupted no effect | Runtime proves the activity did not begin an effect | Inspect and continue from a new turn; no replay needed |
| Read-only corruption | Invalid known event or integrity failure before head | Inspect, export, salvage fork |
| Credential unavailable | Required secret or store missing | Reconfigure, authenticate, or restart; no protected action |
| Cleanup uncertain | Local or remote work may still be active | Inspect and cancel/reconcile; rewind blocked |
| Restore not applied | Denial, cancellation, checkpoint failure, preflight drift, or proven pre-write exit; no `write_attempted` exists | Use the idle context-only child or return to source session |
| Restore recovery required | `write_attempted` exists or an effect cannot be disproved; results may be partial or unknown | Inspect receipt and reconcile manually; normal child turns blocked |
| Restore recovery required | Child fork exists but restore is partial or uncertain | Inspect and reconcile; normal turns blocked |

## 15. Security Acceptance Criteria

### Paths and Authorization

- [ ] Symlink escape, parent traversal, absolute outside path, missing-leaf, and replacement-race tests cannot bypass canonical authorization.
- [ ] A permission decision cannot execute against a changed tool identity, plan digest, resource, runtime generation, or call identity.
- [ ] A once-decision cannot be replayed across sessions, control operations, activities, duplicated call IDs, or concurrent dispatches.
- [ ] Policy cross-product tests prove hard deny and ordinary deny cannot be overridden and project policy only narrows.
- [ ] Project policy attempting to broaden user policy is rejected.
- [ ] An MCP annotation cannot downgrade Yordam-derived risk or bypass a prompt.
- [ ] Restore uses current policy and cannot reuse original edit permission.

### Secrets

- [ ] Literal provider keys, bearer tokens, OAuth access tokens, refresh tokens, and client secrets are rejected from durable config fields.
- [ ] Stdio and command-hook environments contain only allowlisted variables and explicitly bound secrets.
- [ ] Registered synthetic secret byte sequences under supported encodings, including values split across stream deltas, are absent from events, ordinary evidence, receipts, logs, TUI, headless output, and ordinary recovery diagnostics.
- [ ] Confidential restore material is never model-visible, rendered, or included in ordinary export; subjects containing registered secret bytes have exact restore disabled.
- [ ] No plaintext OAuth credential file is created when OS credential storage is unavailable.
- [ ] A secret from one runtime generation cannot leak through output redaction after a reload replaces that generation.

### OAuth and Remote

- [ ] PKCE S256, single-use state, exact redirect URI, protected-resource metadata, authorization-server issuer, resource indicator, and local token issuance binding are validated.
- [ ] Opaque tokens are not described as content-level audience-validated; target enforcement uses stored issuance binding.
- [ ] Tokens are not sent through query strings, untrusted redirects, unrelated hosts, or mismatched MCP resources.
- [ ] SSRF and DNS-rebinding fixtures targeting private or changed addresses are rejected according to configured remote policy.
- [ ] Step-up authorization and reconnect attempts remain bounded.

### Processes and Output

- [ ] Stdio MCP, hook, verifier, and shell output bounds prevent unbounded memory and disk growth.
- [ ] A denied executable verifier starts no process or network activity and verifier mutations remain visible consequential activities.
- [ ] Non-protocol stdout from an MCP server and invalid hook JSON fail safely.
- [ ] Terminal escape sequences from all untrusted sources render as inert text.
- [ ] Cancellation terminates local process groups within the documented bound or records cleanup uncertainty.

### Journal and Recovery

- [ ] Fault injection around every durable barrier never causes automatic mutation replay.
- [ ] A partial event transaction does not affect canonical projection.
- [ ] Concurrent process writers cannot both commit the same expected head.
- [ ] Invalid known payloads expose only the validated prefix and leave source data unchanged.
- [ ] Unknown stateful events and unsupported payload versions permit inspection but block turns, grants, forks, and appends past the validated prefix.
- [ ] Missing or changed evidence invalidates dependent verification rather than silently preserving `verified`.
- [ ] Rewind leaves source journal and source metadata unchanged.
- [ ] Restore drift found during complete preflight causes zero target writes; post-preflight races produce partial recovery state rather than a false success.

## 16. Documentation Requirements

README, SECURITY, TUI help, headless help, generated config comments, receipts, and release notes use these exact distinctions:

- `restricted local` and `trusted local` are policy profiles, not sandboxes;
- checkpoint coverage is explicit and may not include workspace restore;
- context rewind creates a fork;
- exact restore applies only to eligible built-in edits;
- shell and remote effects may be unknown or irreversible;
- MCP authentication does not authorize tool effects;
- project discovery does not imply activation;
- Yordam sends no automatic telemetry.
