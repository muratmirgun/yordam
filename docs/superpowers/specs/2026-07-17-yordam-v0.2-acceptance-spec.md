# Yordam v0.2 Acceptance Specification

Status: approved release-gate design
Date: 2026-07-17
Parent PRD: [Yordam v0.2 Trusted Extensibility](2026-07-17-yordam-v0.2-prd.md)
Normative contract: [Yordam v0.2 Capability Contract](2026-07-17-yordam-v0.2-capability-contract.md)
Internal gate: 4 of 4

## 1. Purpose

This specification defines the evidence required to release Yordam `v0.2.0`. It combines regression, protocol, product-flow, security, recovery, provider, MCP, headless, TUI, packaging, and documentation gates.

Passing unit tests alone is insufficient. Release evidence must show that every consequential side effect obeys durable ordering, every advertised recovery capability matches its actual coverage, and all extension surfaces preserve Yordam's trust model.

## 2. Release-Candidate Identity

Acceptance runs against one exact release-candidate source commit. The acceptance report records:

- source commit and branch or tag;
- Go and toolchain versions;
- supported OS and architecture runners;
- dependency lock state;
- schema and protocol versions;
- MCP core and authorization-profile version targeted by the client, fixed to `2025-11-25` for v0.2;
- provider adapter fixture versions;
- build version, commit, and date metadata;
- archive, checksum, and SBOM digests;
- command lines and result summaries for every gate.

The report itself may be committed after the tested source commit. It must describe evidence lineage without pretending a commit can contain its own future hash.

## 3. Gate Model

Acceptance is cumulative:

| Gate | Required Proof |
|---|---|
| Prerequisite, not a v0.2 gate | Approved JSONC `/reload` baseline and consistent v0.1 acceptance |
| Gate 1: Foundation | Event, journal, migration, evidence, catalogs, authorization, application protocol |
| Gate 2: Trust Loop | Outcome, cockpit, permissions, checkpoint/fork, exact restore, receipts, usage |
| Gate 3: Extensibility | Native providers, MCP, OAuth, project trust, agents/skills, hooks, headless |
| Gate 4: Release Proof | Full regression, adversarial, platform, packaging, docs, and evidence lineage |

A later gate reruns all earlier gate suites. A failure in an earlier suite blocks release even if later features pass.

## 4. Standard Verification Commands

The final repository must provide stable commands equivalent to:

```sh
go test ./...
go test -race ./...
go vet ./...
go test -tags acceptance ./internal/acceptance -run TestV020Acceptance -count=1 -v
go test -race -tags acceptance ./internal/acceptance -run TestV020Acceptance -count=1 -v
```

Provider and MCP conformance suites may use additional documented commands. They must run from a clean checkout without private credentials by using deterministic fixtures or local test servers.

## 5. Prerequisite Acceptance

Before Foundation implementation begins:

1. JSONC configuration and `/reload` match their approved design.
2. README, SECURITY, config schema, generated template, CLI help, and runtime behavior agree on secret storage.
3. Literal provider API-key decoding, schema support, generated output, and persistence are absent; only environment or credential-store references are accepted.
4. The active-turn runtime snapshot remains immutable across reload.
5. Failed reload preserves the complete prior runtime generation.
6. Structurally valid but credential-unavailable configuration has one documented behavior.
7. All fourteen v0.1 real-flow acceptance scenarios pass against the exact baseline commit.
8. The working tree used as the Foundation base is clean except for intentionally generated ignored artifacts.

## 6. Gate 1: Foundation Acceptance

### 6.1 Event and Migration Matrix

Fixtures cover:

- valid pure v0.1 session;
- v0.1 truncated final fragment;
- v0.1 unmatched tool start;
- v0.1 stale edit recovery;
- mixed v1/v2 journal after first v2 append;
- unknown future event kind;
- unsupported future payload version;
- invalid known payload;
- invalid sequence;
- incomplete committed batch;
- missing evidence blob;
- evidence digest mismatch;
- parent/child lineage cycle attempt.

Expected results match the Foundation and Security specifications. No fixture is rewritten unless the test explicitly invokes recovery or migration.

### 6.2 Journal and Concurrency

- expected-head conflicts permit exactly one commit;
- duplicate command IDs and allow-once nonces permit exactly one effect;
- cross-process writer exclusion is tested with separate processes;
- two processes cannot hold active turns in one session simultaneously;
- unrelated sessions do not share one root-wide critical section for normal appends;
- range reads return stable cursors;
- snapshot at `ApplicationCursor` vector plus subscription-after-vector has no cross-journal event gap;
- workspace-control and selected-session durable catch-up reads strictly after each vector component and merge deterministically;
- process-epoch change emits a transient-gap marker and fresh snapshot rather than claiming transient replay;
- slow interactive subscribers cannot cause unbounded queue growth and resume from cursors;
- slow headless stdout causes bounded cancellation rather than silent event loss;
- disposable projections rebuild to the same canonical state at the same journal head.

### 6.3 Durable Ordering

Fault injection stops the process immediately before and after:

- goal/draft commit before contract-drafting provider egress;
- frozen-contract commit before mutation-capable provider phase;
- canonical plan/purpose/resources/digest commit;
- checkpoint and confidential restore-material commit;
- final resource-validation boundary;
- permission-decision commit;
- atomic once-decision consumption and activity-start commit;
- side-effect invocation boundary;
- terminal result and evidence commit;
- provider-result continuation;
- criterion assessment;
- terminal turn/task commit.

Recovery proves no unmatched mutation is automatically repeated and no provider continuation observes an undurable result.

### 6.4 Foundation Exit Evidence

The Gate 1 report includes:

- fixture inventory and digest;
- migration and upcast diagnostics;
- concurrency results;
- fault-injection matrix;
- architecture boundary review confirming orchestration decomposition;
- exact source commit.

## 7. Gate 2: Trust Loop Acceptance

### 7.1 Outcome Scenarios

1. User supplies complete criteria and every criterion verifies.
2. Agent proposes observable criteria before mutation.
3. Agent proposes a weaker contract amendment and the user denies it.
4. Model completes but verification evidence is missing.
5. One criterion verifies and one fails.
6. User explicitly waives a required criterion.
7. Cancellation occurs before contract freeze.
8. Cancellation occurs after one consequential activity.
9. All required criteria are waived and the task becomes `completed_with_waivers`, not verified.
10. A partial or unknown task is explicitly reopened for a new turn without rewriting prior assessment.
11. Missing headless criteria exit contract-required before a mutation-capable provider phase.

Each scenario checks task, criterion, receipt, and user-visible status rather than only final assistant text.

### 7.2 Permission Scenarios

1. R1 inside read resolves without a modal and records disclosure warning.
2. R2 outside read asks with canonical boundary.
3. R3 built-in edit asks with exact diff and restore coverage.
4. R4 outside edit separates preview inspection and write authorization.
5. R5 shell displays unsandboxed local-process effects.
6. Multiple model intents remain FIFO and sequential.
7. `Esc` denies the active request.
8. Cancel terminalizes unresolved queue entries as cancelled.
9. Stale call ID and changed plan digest execute nothing.
10. Session grant lists its true future capability and can be revoked.
11. Broad shell trust uses a separate second confirmation, remains visible, and resets on fork.
12. Cross-session decision replay, duplicated call ID, duplicated nonce, and concurrent dispatch start exactly zero duplicate effects.
13. User/project/grant/interactive policy cross-products prove deny is terminal and project rules only narrow.
14. Taskless MCP start, OAuth, catalog refresh, and recovery use serialized control-operation authorization and do not overlap an active turn effect.

### 7.3 Checkpoint and Restore Scenarios

1. Automatic checkpoint succeeds before built-in edit.
2. Checkpoint persistence fails and edit never starts.
3. Context rewind creates a fork and leaves source journal and workspace unchanged.
4. Fork resets grants, broad shell trust, pending approvals, and transient MCP auth state.
5. Exact single-file edit restore succeeds and verifies content and permissions.
6. Multi-file restore preflight detects one drifted path and writes nothing.
7. Missing preimage bytes disable restore.
8. Shell mutation after checkpoint remains unknown and untouched.
9. Remote-effect evidence remains not reversible.
10. Read-only corruption permits validated-prefix salvage fork only.
11. Mid-turn checkpoint fork bootstraps an idle child and leaves inherited plans non-actionable.
12. Restore creates and blocks the child before workspace writes; a post-write failure leaves that child in recovery-required state.
13. Concurrent drift after successful preflight and one replacement produces a partial receipt and no automatic retry.
14. Repeated edits to one path restore only when their hash chain is contiguous.
15. Registered-secret preimage disables exact restore and keeps raw bytes out of ordinary evidence/export.

### 7.4 Cockpit and Accessibility

Golden and PTY tests cover:

- 60, 80, 119, 120, and 160 columns at 16 and 24 rows;
- terminal-too-small behavior below 60 columns or 16 rows;
- normal color, `NO_COLOR`, reduced-motion, and plain transcript modes;
- wide ledger/inspector and narrow folded timeline;
- permission, diff, checkpoint, restore, recovery, and error surfaces;
- resize while composing, inspecting, and deciding permission;
- keyboard-only navigation;
- clean terminal restoration after normal exit, cancellation, app error, and supported signals.

Critical scope, command, warning, decision lifetime, and unknown-effect text must remain inspectable at all supported sizes.

### 7.5 Usage and Local Metrics

Acceptance proves:

- provider-reported, estimated, and unknown usage are distinct;
- cached and reasoning categories appear only when reported or explicitly estimated;
- unknown pricing does not produce zero cost;
- calculated cost without billing evidence never appears as actual billed cost;
- local metric projection calculates the PRD definitions;
- no automatic telemetry network request occurs;
- explicit metric export contains no secret values.

## 8. Gate 3: Extensibility Acceptance

### 8.1 Provider Contract Matrix

For OpenAI, Anthropic, Gemini, and OpenAI-compatible adapters, deterministic fixtures cover:

- text streaming;
- fragmented tool intent;
- multiple tool intents;
- structured output;
- image/file input capability where supported;
- usage and cache metadata;
- context-window error;
- rate limit and retry-before-first-delta;
- transport-proven pre-send failure permits one bounded retry;
- any unproven-zero send, including header-only, partial-header, 429, EOF, timeout, and empty response after any request byte, permits no automatic retry;
- interruption after content;
- native terminal reasons;
- malformed provider response;
- cancellation;
- missing required capability.
- provider egress decision and context-disclosure plan;
- unknown required capability fails closed;

The matrix records supported, unsupported, and unknown capabilities per adapter. Unsupported required capabilities fail before request.

### 8.2 MCP Transport and Lifecycle Matrix

Deterministic stdio and Streamable HTTP servers cover:

- successful initialization and capability negotiation;
- unsupported protocol version;
- invalid initialize response;
- tools/resources/prompts pagination;
- list-change notification;
- malformed JSON-RPC;
- non-protocol stdio stdout;
- bounded stderr flooding;
- request timeout and cancellation;
- process crash and EOF;
- HTTP JSON response;
- HTTP SSE response;
- session ID lifecycle;
- reconnect with valid stream-local cursor;
- invalid or cross-stream cursor;
- disconnection without cancellation;
- disconnect after remote mutation applies but before response yields uncertain and no automatic resend;
- graceful and forced shutdown.

### 8.3 MCP Item Matrix

- valid and invalid input schemas;
- valid and invalid output schemas;
- text, structured, image, audio, resource-link, and embedded-resource results;
- protocol error versus tool-execution error;
- untrusted destructive/idempotent annotations;
- provider-visible alias collision;
- denied call sends zero `tools/call` messages;
- resource discovery without context insertion;
- explicit resource context inclusion with provenance;
- prompt invocation with source identity;
- prompt or server instruction attempting policy override;
- list change during active turn applies only to future generation.
- `/resources` discovery/activation/deactivation and equivalent headless predeclaration;
- `/prompts` discovery/invocation/deactivation and equivalent headless predeclaration.

### 8.4 OAuth Matrix

Fixtures cover:

- `WWW-Authenticate` resource metadata discovery;
- protected-resource well-known fallbacks;
- OAuth and OpenID Connect authorization-server discovery;
- path-bearing issuer URLs;
- pre-registered client flow;
- Client ID Metadata Document flow where supported by test deployment;
- Dynamic Client Registration where supported;
- DCR secret-bearing or confidential-client response rejection and redaction;
- PKCE S256 success and missing-PKCE refusal;
- state mismatch;
- redirect mismatch;
- missing or incorrect resource indicator;
- opaque-token local issuance binding and target-resource mismatch;
- authorization-server issuer mix-up;
- duplicate or expired callback state;
- token in query rejection;
- insufficient-scope step-up success and bounded failure;
- step-up creates a future-generation credential and never retries the active challenged request;
- refresh-token rotation;
- OS credential-store success;
- unavailable-store process-only fallback;
- headless missing-auth failure;
- SSRF, DNS-rebinding, untrusted redirect, and token-passthrough attacks.

### 8.5 Project Trust and Extension Matrix

- untrusted project discovery activates nothing;
- explicit trust activates approved text and executable sources;
- text-only digest change records new provenance without executable re-approval;
- hook or local-MCP executable digest change requires trust renewal;
- remote MCP endpoint, transport, resource, issuer, or credential reference change requires trust renewal;
- launch-manifest replacement between reload and spawn executes nothing;
- adversarial swap between final hash and spawn executes zero replacement instructions and uses only verified descriptor/staging bytes;
- policy broadening is rejected;
- trust revocation blocks new actions inside an active turn and terminates project processes where possible;
- agent definition selects one agent but spawns no subagent;
- skill activation shows provenance and capability requirements;
- `/agents` and `/skills` activation/deactivation flows and equivalent headless declarations work end-to-end;
- command hooks enforce schema, order, timeout, environment allowlist, recursion guard, and failure policy;
- hook cannot turn deny into allow.
- hook placement relative to plan/checkpoint/authorization/effect/evidence/verification/terminal commit matches the spec;
- a command verifier receives ordinary R5 authorization, and a denied verifier starts no process or network activity.

### 8.6 Headless Matrix

- verified task output is valid JSONL and orderly termination ends with one `RunReceipt` referencing a verified `TaskReceipt`;
- completed-with-waivers, partial, unknown, permission-required, contract-required, configuration, capability, authentication, execution, cancellation, and storage terminals use the public numeric exit table;
- effective `ask` starts no blocked activity and causes no provider continuation after the block;
- `auto` without distinct trusted-shell acknowledgement cannot start shell;
- taskless control-operation JSONL uses journal/control-operation identity without session/task/turn placeholders;
- turn-caused MCP control-operation JSONL uses control-operation identity plus optional task/turn/activity causation and no session-journal ownership claim;
- configuration, capability, authentication, execution, cancellation, and storage failures use stable categories;
- stdout contains only JSONL in JSONL mode;
- stderr contains bounded redacted diagnostics;
- orderly signal cancellation terminalizes durable state where storage and stdout remain available;
- abrupt `SIGKILL` may omit `RunReceipt`, and its absence is recognized as abrupt termination;
- no attach, steering, or approval input path exists.

## 9. Gate 4: Cross-Cutting Security Acceptance

Each adversarial case defines setup, injected fault, observable calls/messages/writes, required durable state, recovery result, and forbidden outcome. The mandatory oracles are:

| Attack or Fault | Required Observable Result | Forbidden Outcome |
|---|---|---|
| Path traversal, symlink, workspace-root, or executable replacement race | Final canonical revalidation rejects changed identity | Any stale-scope file or process effect |
| Swap after final executable hash and before spawn | Verified descriptor/private staging bytes execute, or launch fails | Any instruction from replacement bytes |
| Forged, stale, cross-session, or duplicated approval | Durable deny/conflict; no activity start | Decision replay or duplicate effect |
| User/project/grant policy conflict | Monotonic lattice result with deny preserved | Later layer broadens or overrides deny |
| Malicious provider/MCP control text or terminal escapes | Inert rendered text and preserved content provenance | Policy change or terminal control execution |
| Malicious MCP annotations/instructions/prompts/resources | Conservative Yordam risk and untrusted-content handling | Annotation or content grants authority |
| Oversized/deep/malformed protocol input | Bounded typed failure | Unbounded memory/disk growth or crash |
| Unknown stateful event/payload version | Inspectable read-only validated prefix | Writable downgrade past unknown state |
| Blob/reference/checksum corruption | Verification invalidated and diagnostic | Stale verified status |
| Semantically valid attacker checksum recomputation | Documented as outside v0.2 authenticity guarantees | Claim of attacker-resistant tamper evidence |
| Registered secret split across supported streaming encodings | Redacted ordinary outputs | Registered sequence persisted or displayed |
| Registered secret in binary evidence or confidential-store staging | Ordinary blob withheld; exact restore disabled before any temporary write | Secret-bearing binary or staging file persisted |
| Transformed/unknown child secret | Environment allowlist limits exposure; limitation documented | Claim that all possible transformations are detectable |
| OAuth issuer mix-up, callback replay, redirect, SSRF/DNS, or target mismatch | Auth abort; no token sent to invalid target | Token disclosure or protected request |
| DCR secret-bearing response | Registration rejected; returned secrets redacted and discarded | Client secret or registration token persisted |
| OAuth scope step-up | New future-generation binding; current request terminal | Active request automatically replayed |
| Opaque token | Stored issuance binding enforced | Claim of locally inspected token audience |
| Remote mutation disconnect after apply | Activity uncertain; response resume only | Automatic second mutation request |
| Hook recursion, verifier bypass, fork bomb, output flood, or hang | Depth/timeout/bounds and ordinary authorization enforced | Privileged process or unbounded work |
| Active trust revocation | New project dispatch blocked; process termination attempted | Further project action from frozen generation |
| Crash at durable barrier or during recovery | Last committed state recovered; no blind retry | Automatic mutation replay or silent data loss |
| Preflight restore drift | Zero writes | Any target replacement |
| Concurrent restore drift after first write | Recovery-required child and partial receipt | Success or automatic retry |
| Headless `ask` or missing trusted-shell acknowledgement | Blocked activity never starts; typed `RunReceipt` on orderly termination | Implicit approval from mode alone |

Critical and high findings cannot be risk-accepted for release. They must be fixed or demonstrated to be false positives with reproducible evidence. Medium and low accepted risks are documented with owner, rationale, and expiry.

## 10. Packaging and Platform Acceptance

The release produces exactly one archive and one SPDX SBOM for each target:

- Darwin amd64;
- Darwin arm64;
- Linux amd64;
- Linux arm64.

Acceptance verifies:

- archive architecture;
- version output;
- normal TUI startup and terminal restoration;
- headless JSONL startup and orderly final `RunReceipt`;
- config/schema availability;
- no unexpected network activity without a configured provider or MCP action;
- checksums for every archive and SBOM;
- reproducible release metadata;
- supported platform credential-store adapter behavior or documented process-only fallback.

## 11. Documentation Consistency Gate

Automated or review-backed checks ensure README, SECURITY, CLI help, TUI help, generated config, schema descriptions, release notes, and all v0.2 specs agree on:

- configuration and secret-value policy;
- provider adapter names and capability behavior;
- MCP transports, surfaces, and OAuth behavior;
- project trust and executable-digest renewal;
- `restricted local` and `trusted local` not being OS sandboxes;
- checkpoint coverage and context-fork semantics;
- exact built-in edit restore limits;
- shell and remote-effect uncertainty;
- headless fail-closed permissions;
- local metrics, local persistence/control plane, explicit configured network actions, and no automatic telemetry;
- v0.1 read compatibility and v0.2 downgrade limits.

Any contradiction in a security or data-loss promise blocks release.

## 12. Product Pilot

Before final release, 10 to 20 representative local tasks are run across at least:

- debugging and test repair;
- small feature implementation;
- refactoring with no public API change;
- documentation-only work;
- a task using one native provider tool loop;
- a task using MCP read-only context;
- a task using an authorized remote MCP mutation;
- a denied-risk task;
- context rewind;
- exact edit restore.

The pilot produces local metric reports for:

- verified completion rate;
- interventions per verified task;
- approvals per task by risk class;
- receipt coverage;
- successful restore rate;
- state-understanding time;
- uncertain-effect rate.

The pilot establishes a baseline and reveals product regressions. It does not introduce arbitrary release targets after implementation. Any false verification, hidden mutation, unrecoverable source-session damage, or secret leak blocks release regardless of aggregate metrics.

## 14. Release Decision

`v0.2.0` may ship only when all checklist items pass. There is no preview carve-out for incomplete provider, MCP, trust, checkpoint, restore, receipt, or headless behavior. If a mandatory scope item is incomplete, schedule moves; the trust and quality bar does not.
