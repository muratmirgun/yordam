## 1. Purpose

Extensibility adds native providers, MCP tools/resources/prompts, user and project agent definitions, instructions, skills, hooks, and headless execution without creating privileged paths around Yordam's outcome, activity, evidence, permission, checkpoint, and receipt contracts.

Every extension source has a canonical identity, provenance, trust state, runtime generation, capability set, and failure boundary. Discovery never implies activation. Authentication never implies authorization. Provider compatibility never implies silent feature emulation.

## 2. Goals

Extensibility must:

1. support native OpenAI, Anthropic, and Gemini provider adapters;
2. retain a separately identified OpenAI-compatible adapter;
3. negotiate model capabilities and expose actual usage, context, caching, and terminal metadata;
4. support MCP tools, resources, and prompts;
5. support MCP stdio and Streamable HTTP transports;
6. implement MCP lifecycle and protocol-version negotiation;
7. implement remote bearer credentials and MCP-compliant OAuth 2.1;
8. keep MCP server authentication separate from action authorization;
9. support user and explicitly trusted project agents, instructions, skills, MCP definitions, and hooks;
10. re-request trust when executable project provenance changes;
11. support declarative and command hooks with typed phases and bounded effects;
12. provide a versioned headless JSONL event stream, deterministic exit contract, and orderly final `RunReceipt`;
13. preserve active-turn runtime-generation immutability during reload and catalog changes;
14. ensure all extension actions participate in Trust Loop risk and evidence projection.

## 3. Non-Goals

- provider or MCP marketplace and installer;
- automatic execution of repository-owned commands before workspace trust;
- custom binary plugin ABI or in-process dynamic library loading;
- legacy MCP HTTP+SSE transport unless a later compatibility decision explicitly adds it;
- MCP sampling, elicitation, or task-augmented execution in v0.2;
- automatic loading of every MCP resource into model context;
- treating MCP server instructions or annotations as trusted policy;
- custom provider adapter loading from project code;
- bidirectional headless approvals or remote session attach;
- subagents, parallel actions, or remote runners;
- OS-level sandbox guarantees.

## 4. Configuration and Resolution

The completed JSONC `/reload` prerequisite remains the only global configuration mechanism. Extensibility expands its schema with versioned sections for:

- providers and models;
- MCP servers;
- agents;
- instruction sources;
- skills;
- hooks;
- authorization policy;
- execution profiles;
- headless defaults;
- limits and pricing metadata.

Project definitions use a documented repository-owned location under the canonical workspace. Project files are parsed and validated before trust but remain inactive until the workspace-trust requirements in this specification pass.

### 4.1 Resolution Order

Effective definitions resolve in this order:

1. built-in defaults;
2. user configuration;
3. explicitly trusted project configuration;
4. session selection;
5. turn-scoped selection supplied directly by the user.

Later layers may select or narrow earlier behavior. Project configuration cannot broaden user hard-deny policy, credential access, or execution guarantees.

### 4.2 Runtime Generation

Reload follows prepare-then-swap:

1. parse and validate all sources;
2. resolve trust and credentials without exposing secret values;
3. build provider, MCP, agent, instruction, skill, hook, catalog, authorization, and execution candidates;
4. build a pure candidate without launching processes, contacting endpoints, opening OAuth, or fetching remote catalogs;
5. persist required selection changes;
6. atomically activate one complete semantic runtime-generation manifest for future turns;
7. retain the prior generation on structural, construction, or required-persistence failure.

Connection, authentication, probing, and catalog fetch always occur as authorized, serialized `ControlOperation` lifecycles in the workspace control journal. When a turn requires the connection, the control operation carries that task/turn/activity as causation and the turn waits for its terminal result. An unresolved `ask` opens a control-operation permission card in the TUI and fails closed in headless mode. Consequential control operations never run in the background alongside another consequential effect.

An active turn retains its original semantic generation. Mutable transport and credential leases may refresh only inside the serialized effect lane and only when server identity, resource, issuer, client, scope, source revision, and policy constraints remain unchanged. A catalog or authorization-semantic change requires a future runtime generation. Live hard-deny and trust-revocation overlays are checked before every dispatch.

## 5. Provider Architecture

### 5.1 Adapter Kinds

v0.2 ships these adapter kinds:

- `openai`;
- `anthropic`;
- `gemini`;
- `openai_compatible`.

Provider profile identity is separate from adapter kind. Multiple profiles may use the same adapter with different endpoints, credentials, and model catalogs.

### 5.2 Provider-Neutral Content

The normalized request and response model uses content blocks for:

- text;
- structured JSON;
- tool intent and tool result;
- image and file input where supported;
- refusal or safety response;
- provider-exposed reasoning summary where supported and allowed;
- usage, cache, and terminal metadata.

Adapters translate explicitly between native protocols and this representation. A native feature is not forced into text when doing so would erase required semantics.

### 5.3 Model Descriptor

Each configured model resolves to a descriptor containing known or declared:

- provider and adapter identity;
- display name and model ID;
- context window and maximum output;
- supported input content types;
- streaming support;
- tool-use support;
- parallel-tool-intent support;
- structured-output or JSON-schema support;
- prompt-cache controls and usage reporting;
- provider reasoning-summary support;
- token-counting support;
- usage categories reported by the provider;
- pricing and currency provenance;
- source and runtime generation.

Each capability has `supported`, `unsupported`, or `unknown` state plus source and runtime generation. Precedence is adapter protocol guarantee, live negotiated fact, bundled versioned metadata, then user-configured claim. A lower-precedence source cannot contradict a higher-precedence fact; contradiction makes the candidate invalid. User overrides remain labeled configured claims rather than provider facts.

### 5.4 Capability Requirements

A turn or feature declares capabilities as `required`, `preferred`, or `unused`.

- Required capability proceeds only when state is `supported`. `unsupported` and `unknown` fail with `capability_unavailable` before network request.
- Missing preferred capability: use a documented semantically safe path and record the negotiated plan and warning.
- Unused capability: no negotiation requirement.

Examples:

- Built-in tool execution requires tool use.
- A strict structured receipt request may require schema-constrained output.
- Image input requires image capability.
- Prompt caching is preferred and may be absent without changing task semantics.

Provider support for parallel tool intents does not enable parallel Yordam execution. Intents are validated, queued, and executed sequentially in model order.

### 5.5 Stream and Terminal Semantics

Normalized provider events include:

- content delta;
- completed content block;
- tool intent;
- usage update;
- provider request ID where available;
- rate-limit metadata where available;
- terminal reason;
- retry classification, including whether transport proves zero request bytes were sent;
- typed error.

Terminal reasons preserve native meaning where possible and map to stable categories such as `completed`, `tool_use`, `max_output`, `content_filtered`, `context_exceeded`, `cancelled`, and `provider_error`.

Automatic provider retry is allowed only when the transport proves zero request bytes were sent. A partial header write, 429, timeout, EOF, or empty response after any request byte is not automatically retried because disclosure and billing may already have occurred. The attempt terminalizes as interrupted or unknown and the user may start a new explicit turn. Once user-visible content or a tool-intent delta is emitted, a new provider attempt is never silently substituted.

### 5.6 Usage and Cost

Adapters normalize provider-reported input, output, cached, cache-write, and reasoning usage without manufacturing unsupported categories. Each usage value includes `provider_reported`, `estimated`, or `unknown` status.

Cost is derived from versioned pricing configuration and usage evidence. The ledger records pricing source, effective date or version, currency, and `calculated`, `actual_billed`, or `unknown` status. Local calculation never becomes `actual_billed` without provider billing evidence. Unknown pricing yields unknown cost.

### 5.7 Provider Egress Authorization

Every provider request is a consequential disclosure and cost activity. Before request bytes are sent, Yordam durably records and authorizes:

- canonical endpoint and provider/model identity;
- credential binding identity;
- context-plan digest and source-provenance summary;
- disclosed content classes and outside-workspace sources;
- required capability plan;
- configured token/cost budgets;
- retry policy and runtime generation.

Configured user policy may allow ordinary requests to an approved provider/model without a modal. Project policy may only narrow that allowance. Headless mode fails before network egress when the effective provider decision is `ask`.

## 6. MCP Client

### 6.1 Supported Surfaces

v0.2 supports:

- server tools;
- server resources;
- server prompts.

MCP sampling, elicitation, roots mutation, and task-augmented execution are not advertised unless a later approved specification adds them.

### 6.2 Lifecycle

Every connection follows as a `ControlOperation`, optionally caused by a task activity:

```text
configured
-> authenticating when required
-> initialize request
-> protocol and capability negotiation
-> initialized notification
-> catalog synchronization
-> ready
-> disconnecting | auth_required | incompatible | failed
```

The initialization exchange is the first protocol interaction. Yordam sends the latest MCP protocol version it supports, accepts only a supported negotiated version, advertises only implemented client capabilities, and uses only server capabilities negotiated successfully.

No tool, resource, prompt, or server instruction becomes active or model-visible before `ready`.

### 6.3 Stdio Transport

For stdio servers:

- Yordam launches the configured executable as a child process;
- stdin and stdout carry newline-delimited UTF-8 MCP JSON-RPC only;
- non-protocol stdout is a protocol failure;
- stderr is bounded diagnostic output and does not itself imply request failure;
- environment starts from an explicit allowlist plus named secret references;
- provider credentials and unrelated environment secrets are absent;
- process start uses the selected local execution-policy profile and project trust;
- process start has a durable canonical launch-manifest digest and ordinary R5 authorization before spawn;
- executable, interpreter/script, arguments, working directory, environment names, credential bindings, declared dependency locks, and resolved bytes are verified through the race-resistant launch adapter before spawn;
- shutdown closes stdin, waits a bounded interval, sends graceful termination, then force-kills the process group if necessary;
- unconfirmed termination is recorded as uncertain cleanup.

Stdio MCP OAuth is not used. Credentials are resolved from explicit environment references as recommended by the MCP transport model.

### 6.4 Streamable HTTP Transport

For remote servers:

- one configured MCP endpoint supports POST and optional GET SSE;
- requests accept JSON and event-stream responses as required by MCP;
- session IDs and negotiated protocol-version headers are handled securely;
- reconnect and resumability use server event IDs only within the correct MCP stream;
- disconnection is not treated as cancellation;
- cancellation uses the MCP cancellation mechanism where supported;
- request, connection, and absolute maximum timeouts are enforced;
- authorization headers are sent on every protected request and never placed in the URI;
- redirect targets and origins are validated according to the client security policy;
- remote effects are labeled remote and are not attributed to local execution profiles.
- once a mutation-capable POST request may have reached the server, Yordam never resends it automatically; reconnect may resume its response stream but cannot replay the request. Retry is a new explicitly planned and authorized activity, and the original remains uncertain.

Legacy HTTP+SSE fallback is not part of v0.2.

### 6.5 Canonical Identities and Aliases

Canonical identities are structured records, not delimiter-concatenated display strings. A server identity contains logical server ID, transport and canonical endpoint or launch-manifest identity, source revision, and configuration digest. An item identity contains logical item name or canonical resource URI plus descriptor/schema digest and server source revision.

Provider-visible tool aliases satisfy the selected provider's name constraints and are unique within the turn. The mapping to canonical identity is durable. Authorization, grants, evidence, and receipts bind logical identity plus source revision and descriptor digest; a session grant cannot silently apply to changed item semantics.

### 6.6 Tools

MCP tools are adapted into Yordam execution plans. Before `tools/call`:

1. tool identity and input schema are validated;
2. arguments are validated;
3. source and server trust are resolved;
4. Yordam derives conservative effect, boundary, execution-locus, reversibility, and verification facts;
5. server annotations are displayed as untrusted hints and never become policy authority, even when connection trust exists;
6. the action enters the normal authorization queue;
7. the effective decision is durable.

Denial sends no `tools/call` request.

Tool results preserve text, structured content, images, audio, resource links, and embedded resources as typed evidence. Output schemas are validated when supplied. Malformed or schema-invalid output is not silently passed to the model as valid structured data.

Protocol errors and tool-execution errors remain distinct. Bounded actionable tool errors may be returned to the model; protocol failures are normally terminal for that connection or action.

If a connection drops after a remote tool may have applied a mutation but before the response is complete, the activity becomes `uncertain`. Yordam may resume the existing response stream using MCP stream cursors, but it does not send a second `tools/call` request automatically.

### 6.7 Resources

MCP resources are discoverable context sources, not automatically trusted model context.

Resource use requires:

- explicit user selection, agent request through an approved context plan, or an explicitly activated trusted skill/agent dependency;
- canonical server and resource URI;
- boundary and disclosure evaluation;
- authorization when reading or disclosing the resource requires it;
- evidence provenance, media type, annotations, and digest where content is fetched;
- context-budget inclusion or exclusion reason.

Subscriptions and list-change notifications may update future runtime generations. v0.2 does not require resource subscription support unless the server and client explicitly negotiate it.

Interactive users discover resources through `/resources` or the command palette, inspect server/URI/provenance, and choose `add to next context` or `remove from context`. An agent request for a resource creates the same visible context-plan activation and authorization flow. Headless runs list resource IDs in task input, agent definition, or skill configuration; an undeclared agent request that resolves to `ask` fails closed.

### 6.8 Prompts

MCP prompts are discoverable templates. They do not execute tools and are never inserted silently.

A prompt invocation records:

- canonical server/prompt identity;
- supplied arguments;
- source trust and runtime generation;
- returned messages and content types;
- user or agent activation reason;
- context-plan inclusion and digest.

Server-provided instructions and prompt content are untrusted content. They cannot override Yordam system policy, user hard-deny policy, outcome contracts, or secret boundaries.

Interactive users discover and invoke prompts through `/prompts` or the command palette, provide schema-validated arguments, preview provenance, and add returned messages to the next context plan. Headless runs predeclare prompt identity and arguments in task input, agent, or skill configuration. Prompt deactivation removes it from future context plans and never rewrites historical context manifests.

### 6.9 Catalog Changes

When a ready server reports tool/resource/prompt list changes:

1. Yordam records the notification without changing the active catalog;
2. after the active turn is terminal, an authorized serialized control operation fetches and validates the new list in isolation;
3. alias collisions, invalid schemas, and unsupported content fail the candidate catalog;
4. a new runtime generation activates for the next turn;
5. removed items do not invalidate already durable historical identity.

## 7. MCP Authentication

### 7.1 Bearer Secret References

A remote server may reference a bearer token through a named secret binding. Literal token values are rejected in config. The token is sent only in the `Authorization` header to the canonical configured resource and is redacted from all diagnostics.

### 7.2 OAuth 2.1 Profile

v0.2 targets MCP authorization profile `2025-11-25`. Upgrading that profile requires a reviewed spec amendment and conformance update. Interactive remote OAuth implements:

- initial protected-resource request and 401 handling;
- `WWW-Authenticate` resource-metadata parsing;
- protected-resource metadata well-known fallback;
- authorization-server metadata and OpenID Connect discovery;
- pre-registered clients, Client ID Metadata Documents where deployment support exists, and Dynamic Client Registration only for public clients with `token_endpoint_auth_method=none`;
- authorization-code flow with PKCE S256;
- exact redirect handling on localhost or HTTPS;
- unpredictable state generation and verification;
- RFC 8707 resource indicators in authorization and token requests;
- local issuance binding to the exact protected-resource metadata URL, canonical resource identifier, authorization-server issuer, client ID, requested scopes, and runtime generation;
- bounded scope selection and step-up authorization;
- refresh-token rotation when provided;
- bounded retries and terminal auth errors.

If server metadata does not advertise PKCE support, Yordam refuses the OAuth flow. Issuer mix-up checks bind the authorization response and token endpoint to discovered metadata. Callback state is single-use and expires after a bounded interval. For opaque tokens, Yordam validates local issuance binding rather than claiming inspection of token audience contents. Tokens are never sent to a resource other than the one in that binding. DCR responses containing a client secret, registration access token, or confidential-client method are rejected; returned secret values are immediately registered for redaction and discarded.

Successful OAuth scope step-up creates a new credential binding and future runtime generation. It never retries the challenged active request. The current activity terminalizes as authentication-required or uncertain according to whether the challenged request could have had an effect; the user may retry under the new generation. Headless mode does not perform step-up.

### 7.3 Token Storage

- macOS uses Keychain through an appropriate system credential adapter.
- Linux uses Secret Service through an appropriate system credential adapter.
- Unsupported or unavailable credential stores cause process-memory-only token storage.
- There is no plaintext credential-file fallback.
- Events record credential binding identity and status, never token material.
- Credential-store lookup identity includes protected-resource metadata URL, canonical resource, authorization-server issuer, client ID, granted scopes, and account identity when available.

### 7.4 Headless OAuth

Headless mode does not launch an interactive browser flow. It may use an already valid credential-store binding or configured bearer reference. Missing, expired, or insufficient credentials fail closed with an authentication-required `RunReceipt` on orderly termination and no protected MCP action.

### 7.5 Authentication Versus Authorization

Successful OAuth or bearer authentication means only that the MCP server accepts the connection. Each tool call, resource read, prompt use with consequential disclosure, or remote mutation still receives a separate Yordam authorization decision. Yordam does not perform token passthrough; it cannot guarantee an independently implemented remote server's downstream behavior.

## 8. Agent Definitions

An agent definition may select or constrain:

- display name and description;
- system instruction sources;
- default skills;
- provider/model capability requirements;
- tool and MCP item allowlist;
- execution-profile default;
- authorization defaults that do not broaden user policy;
- token and cost budgets;
- outcome-contract template;
- verification policy;
- hooks.

Agent definitions do not spawn subagents in v0.2. One selected definition configures the single active agent.

The ledger records selected agent ID, source scope, digest, and runtime generation for every turn.

## 9. Instructions and Skills

### 9.1 Instruction Sources

Instruction sources have:

- canonical source identity and path or package reference;
- user, project, built-in, MCP, or session scope;
- content digest and version;
- trust state;
- deterministic precedence;
- activation reason;
- context-budget contribution.

The context planner shows included and excluded sources. Conflicts do not resolve through hidden ordering; effective precedence is inspectable.

### 9.2 Skills

A skill is a reusable bundle of:

- instruction content;
- activation description;
- optional tool, MCP, provider-capability, execution-profile, and verification requirements;
- source provenance and digest.

Skill activation is explicit through user selection, selected-agent default, or visible agent request. A skill cannot grant itself permissions, activate an untrusted project executable, or bypass context budgeting.

Interactive users discover, activate, and deactivate agents and skills through `/agents`, `/skills`, or the command palette. Activation previews source, digest, required tools/MCP items, provider capabilities, execution profile, verification requirements, and policy narrowing. Headless task input names every activated agent and skill; an undeclared agent-requested activation that resolves to `ask` fails closed.

## 10. Workspace Trust

### 10.1 Discovery Before Trust

Project sources may be parsed and listed before trust so the user can inspect:

- source files and digests;
- requested agents, skills, MCP servers, commands, hooks, credentials, and policy changes;
- executable commands and environment references;
- whether requested policy narrows or attempts to broaden user policy.

Before trust, no project instruction enters model context and no project executable, MCP server, or command hook starts.

### 10.2 Trust Decision

Workspace trust is bound to:

- canonical workspace identity;
- user configuration generation;
- trusted project configuration set;
- executable launch manifests, resolved source digests, and declared dependency manifest or lockfile digests;
- remote MCP endpoint, transport, and canonical resource identity;
- requested credential references;
- effective policy delta.

Trust is durable and revocable.

### 10.3 Re-Approval

Re-approval is required when:

- a command-hook executable, arguments, working directory, or environment allowlist changes;
- a local MCP launch command or environment changes;
- a remote MCP endpoint, transport, canonical resource, OAuth issuer binding, or bearer credential reference changes;
- a project policy requests broader capabilities;
- a project definition adds a new executable source or credential reference.

Text-only instruction, prompt, or skill-content changes do not invalidate workspace trust, but their new source digest and runtime generation are visible before the next turn and in the ledger.

For every project-owned process start, Yordam opens source files without following untrusted replacements, hashes bytes from those open handles, and creates a private mode-`0700` staging directory containing mode-`0500` verified copies, or executes verified descriptors through an OS primitive where supported. Scripts and trusted interpreter identity are staged or descriptor-bound as applicable. The repository pathname is never used for final spawn. Final manifest validation, live revocation-epoch check, and process registration are linearized under the dispatch lock immediately before spawn. Workspace-root replacement, symlink swap, PATH resolution change, interpreter change, script-byte change, declared lockfile change, or credential-binding change blocks execution and requires renewed trust. Undeclared runtime-loaded dependencies remain an explicit unsandboxed-process limitation.

Trust revocation creates a live deny overlay checked before every dispatch. It blocks new project-owned activity in active turns, terminates project-owned processes where possible, and records `uncertain` when termination or external effects cannot be confirmed.

## 11. Hooks

### 11.1 Supported Phases

v0.2 supports typed phases:

- `pre_action`;
- `post_action`;
- `permission`;
- `turn_complete`;
- `verification`.

All hook invocations are activities with inputs, outputs, duration, terminal state, and evidence.

### 11.2 Declarative Hooks

Declarative hooks may:

- annotate an activity;
- add a hard deny or require interactive approval;
- require named verification before a criterion can pass;
- require a checkpoint class;
- narrow tool, resource, execution-profile, or network policy;
- emit a bounded diagnostic.

They cannot broaden user policy, grant credentials, remove required criteria, or transform a denied action into allowed.

### 11.3 Command Hooks

Command hooks:

- require user configuration or explicitly trusted project provenance;
- run under `restricted local` or `trusted local`, never an implied sandbox;
- receive redacted, versioned JSON through stdin;
- emit one bounded, schema-validated JSON result on stdout;
- write bounded diagnostics to stderr;
- have per-hook and absolute timeouts;
- inherit only an explicit environment allowlist;
- cannot invoke themselves recursively;
- pass through ordinary authorization when their execution or requested result is consequential.

Command-hook result types are `observe`, `veto`, `require_approval`, `require_verification`, and `diagnostic`. A hook cannot directly return `allow` to override a deny.

### 11.4 Ordering and Failure Policy

Hooks have deterministic configured order. Each definition chooses one failure policy:

- `continue_with_diagnostic` for observational hooks;
- `fail_activity` for required enforcement hooks;
- `fail_turn` for required turn-complete or verification hooks.

Timeout follows the selected failure policy. Unlimited retry is prohibited. Hook-triggered diagnostics do not recursively invoke the same phase.

Hook placement is fixed:

1. `pre_action` runs after the initial canonical plan is durable and before checkpointing; it may narrow or veto, and any change produces a new plan digest.
2. Checkpoint preparation completes.
3. Every command `permission` hook runs before final resource revalidation; it may veto, require ask, or diagnose but cannot alter plan/resources.
4. Final resource validation, authorization commit, and target effect run.
5. Terminal effect evidence commits.
6. Every command `post_action`, `verification`, and `turn_complete` hook runs before the final verifier suite. Such hooks may diagnose or fail continuation but cannot rewrite observed evidence.
7. The final verifier suite runs after all mutation-capable hooks. A hook mutation is a visible child activity and invalidates earlier receipts for affected subjects.
8. Declarative-only `verification` hooks evaluate final verifier receipts before criterion assessment.
9. Declarative-only `turn_complete` hooks run after criterion assessment and before terminal turn/task commit.

A command hook is itself a consequential child activity on the same serialized lane. Its authorization evaluates base policy while excluding hook nodes already on the current invocation stack, preventing permission-hook recursion. Maximum hook invocation depth is four; a repeated hook/phase pair or deeper graph fails according to the hook's failure policy.

Executable verifiers use the same R5 process path, authorization, checkpoint rule, environment allowlist, process group, bounds, and uncertainty handling as shell and command hooks. Verification does not create a privileged execution path.

## 12. Headless Mode

### 12.1 Command Surface

v0.2 exposes one non-interactive run path that accepts:

- workspace;
- task prompt and optional outcome contract input;
- session creation or continuation selection;
- agent and model selection;
- permission mode and preconfigured policy source;
- JSONL output selection;
- explicit limits and cancellation signal handling.
- at least one required completion criterion;
- predeclared resource, prompt, agent, and skill activations;
- a distinct noninteractive trusted-shell acknowledgement when shell capability is intended; `auto` mode alone is insufficient.

The exact CLI spelling is defined in the implementation plan and CLI review, but semantics in this section are fixed.

### 12.2 JSONL Stream

Every line is one versioned object containing:

- stream schema version;
- stream event ID;
- session, task, turn, and activity IDs where applicable;
- timestamp;
- kind;
- durable or transient classification;
- journal cursor for durable events;
- structured payload;
- redacted stable error code and message.

On orderly termination while stdout and storage remain writable, the final line is one `RunReceipt` union referencing applicable `TaskReceipt`, `ActivityReceipt`, `VerificationReceipt`, `RestoreReceipt`, or typed permission/auth/config/storage terminal details. `SIGKILL`, process death, or broken stdout may prevent a final line; absence of `RunReceipt` is the defined indication of abrupt termination. Process output outside JSONL is prohibited when JSONL mode is selected. Diagnostics use a separately documented stderr contract and contain no registered secret values.

### 12.3 Permission Behavior

Headless mode has no interactive approval input. Effective `allow` and `deny` decisions behave normally. Effective `ask`:

1. writes a durable permission-required terminal state;
2. starts no blocked action and performs no provider continuation after the block;
3. emits a permission-required `RunReceipt` with the required canonical capability and policy provenance on orderly termination;
4. exits with the `permission_required` exit code.

### 12.4 Exit Categories

Stable semantic categories are:

- verified success;
- completed with waivers;
- partial;
- unknown;
- permission required;
- contract required;
- configuration invalid;
- capability unavailable;
- authentication required;
- execution or verification failure;
- cancelled or interrupted;
- storage corrupt or unavailable.

The public numeric exit contract is:

| Code | Category |
|---:|---|
| 0 | verified success |
| 2 | completed with waivers |
| 3 | partial |
| 4 | unknown |
| 10 | permission required |
| 11 | contract required |
| 12 | configuration invalid |
| 13 | capability unavailable |
| 14 | authentication required |
| 15 | execution or verification failure |
| 16 | storage corrupt or unavailable |
| 130 | cancelled or interrupted after orderly signal handling |

### 12.5 No Attach Protocol

v0.2 does not support sending approval responses, steering, or attach commands to a running headless process. Future bidirectional control requires a separate authenticated transport design.

## 13. System States and Errors

| State or Error | Expected Behavior |
|---|---|
| Provider capability absent | Fail before provider request; show required and available capabilities |
| Native terminal reason unknown | Preserve provider-native diagnostic and map stable category to unknown provider terminal |
| MCP version incompatible | Disconnect before catalog exposure |
| Invalid MCP schema | Reject item or candidate catalog; keep previous runtime generation |
| MCP list changed during turn | Active catalog remains frozen; authorized refresh waits until the turn is terminal |
| OAuth metadata invalid | Abort auth; send no token to unvalidated resource |
| OAuth credential store unavailable | Keep token process-only; inform user re-auth will be required |
| MCP tool denied | Send no `tools/call`; return structured denial to model when safe |
| MCP result schema invalid | Record evidence and typed validation failure; do not mark structured output valid |
| Project untrusted | List discovered sources but activate none |
| Executable digest changed | Invalidate relevant trust and block activation pending re-approval |
| Hook timeout | Apply configured bounded failure policy and record an activity receipt |
| Headless action asks | Start no blocked action; emit permission-required `RunReceipt` on orderly termination and exit |

## 14. Acceptance Criteria

### Providers

- [ ] Given each native provider adapter, when a contract fixture streams text, tool intent, usage, and a terminal reason, then normalized events preserve order and native meaning.
- [ ] Given an OpenAI-compatible profile, when resolved, then it remains identified as `openai_compatible` rather than native OpenAI.
- [ ] Given a missing required capability, when a turn starts, then no provider network request occurs.
- [ ] Given provider parallel tool intents, when received, then Yordam displays their order and executes them sequentially.
- [ ] Given unknown pricing, when usage completes, then cost remains unknown rather than zero.
- [ ] Given content emitted before interruption, when the adapter fails, then Yordam does not silently restart a fresh attempt.
- [ ] Given transport proves zero request bytes were sent, when a retryable pre-send failure occurs, then one bounded automatic retry may run as a new provider attempt.
- [ ] Given 429, EOF, timeout, or empty response after request-body transmission, when the attempt fails, then no automatic retry occurs.

### MCP Lifecycle and Catalog

- [ ] Given a compatible stdio or Streamable HTTP server, when initialized, then protocol and capabilities negotiate before any item is catalog-visible.

### Project Trust, Agents, Skills, and Hooks

### Headless

- [ ] Given a headless verified task and orderly termination, when it exits, then stdout is valid JSONL ending in one `RunReceipt` that references a verified `TaskReceipt`, and exit code is 0.

## 15. Gate Exit

Extensibility exits only when:

- Foundation and Trust Loop acceptance remain green;
- provider contract fixtures pass for all four adapter kinds;
- MCP transport, lifecycle, item, catalog-change, and OAuth conformance suites pass;
- every extension source participates in the same Trust Loop authorization and evidence flow;
- no project executable activates without effective workspace trust;
- headless `ask` behavior is proven side-effect-free;
- the Gate 3 evidence records one exact source commit.
