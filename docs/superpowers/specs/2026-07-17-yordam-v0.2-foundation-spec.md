# Feature Spec: Yordam v0.2 Protocol Foundation

Status: approved design
Date: 2026-07-17
Parent PRD: [Yordam v0.2 Trusted Extensibility](2026-07-17-yordam-v0.2-prd.md)
Normative contract: [Yordam v0.2 Capability Contract](2026-07-17-yordam-v0.2-capability-contract.md)
Internal gate: 1 of 4

## 1. Purpose

Protocol Foundation creates the stable execution, persistence, evidence, catalog, authorization, and application boundaries required by every user-visible v0.2 capability. It replaces implicit ordering and feature-specific replay logic with versioned contracts while retaining the one-process, one-active-turn operating model.

This gate is intentionally foundation-first. It does not ship the final cockpit, rewind commands, MCP client, native providers, or project extensions. It must prove that those later capabilities can be added without growing the existing turn runner into a larger monolith or weakening v0.1 recovery guarantees.

## 2. Current Constraints

The implementation begins from these v0.1 constraints:

- `internal/agent.RunTurn` owns provider streaming, context assembly, tool planning, permission, execution, persistence, redaction, and terminal classification.
- Durable events have session sequence identity but no explicit task, turn, activity, parent, actor, or causation identity.
- Event validation accepts any non-empty kind with any valid JSON payload and requires envelope schema version 1.
- The session port supports create, full load, list, and single append but not expected-head append, event ranges, atomic batches, or lineage.
- Loading a session may perform recovery mutations, and append validation scans the complete log.
- Artifacts are addressed through session-local paths rather than content digests and evidence provenance.
- The provider port exposes one stream method and the tool registry is fixed to four built-ins.
- Permission requests use an unstructured scope and built-in-name classification.
- TUI and app events contain internal Go values rather than a versioned presentation protocol.

## 3. Goals

Foundation must:

1. define stable task, turn, activity, actor, evidence, checkpoint, provider, tool, and runtime-generation identifiers;
2. define a versioned event envelope and typed payload codec registry;
3. read v0.1 sessions through deterministic in-memory upcasting;
4. support expected-head, per-session, committed-batch appends;
5. separate read, recovery, and migration operations;
6. support event-range reads and rebuildable projections;
7. store evidence metadata separately from content-addressed blobs;
8. introduce activity, task, outcome, and authorization projections;
9. decompose turn execution into bounded services coordinated by an orchestrator;
10. replace built-in-specific provider and tool registries with catalogs;
11. introduce structured authorization requests and decisions;
12. introduce provider-neutral content blocks and capability descriptors;
13. define a versioned application command, snapshot, and event protocol shared by TUI and headless adapters;
14. retain all v0.1 durable-before-side-effect and recovery behavior.

## 4. Non-Goals

- final operator-cockpit visual implementation;
- public checkpoint, rewind, or restore commands;
- native provider network adapters;
- MCP transports or OAuth;
- project agent, instruction, skill, or hook loading;
- headless CLI release behavior;
- parallel tools, multiple active turns, or subagents;
- database migration to a server or cloud service;
- cryptographic signing or identity attestation.

## 5. Architecture

### 5.1 Target Boundaries

```text
TUI adapter -------------------+
                               |
Headless adapter ----> Application Protocol
                               |
                               v
                     Application Service
                               |
                               v
                       Turn Orchestrator
             +----------+-----+------+----------+
             |          |            |          |
        Context      Provider     Execution   Verification
        Planner      Service      Planner     Service
                                  + Auth
             |          |            |          |
             +----------+-----+------+----------+
                               |
                 Event Journal + Evidence Store
```

The orchestrator owns lifecycle and ordering. It does not implement provider translation, context budgeting, tool-specific planning, policy evaluation, evidence storage, or UI projection.

### 5.2 Recommended Package Responsibilities

Exact package names may change during implementation, but ownership must remain distinct:

| Boundary | Responsibility |
|---|---|
| `internal/protocol` | Stable identifiers, application DTOs, event envelope, payload versions |
| `internal/journal` or evolved `session/jsonl` | Append, range read, recovery, migration, lineage storage |
| `internal/activity` | Activity lifecycle model and projection |
| `internal/evidence` | Evidence metadata, content-addressed blob storage, links |
| `internal/task` or `internal/outcome` | Task and outcome-contract projection |
| `internal/orchestrator` or narrowed `internal/agent` | Turn lifecycle and durable ordering |
| `internal/context` | Context-source resolution, budgeting, and context plans |
| `internal/provider` | Provider-neutral catalog, descriptors, requests, and stream normalization |
| `internal/tooling` | Dynamic tool catalog, execution plans, provider-visible aliases |
| `internal/authorization` | Structured policy evaluation, grants, and provenance |
| `internal/verification` | Verifier contracts and receipt model |
| `internal/application` or evolved `internal/app` | Commands, snapshots, subscriptions, runtime generations |

No new global mutable service locator may replace the current large runner. Composition remains in `internal/app`, but behavior belongs to bounded interfaces.

## 6. Identifiers and Correlation

The canonical model includes opaque, globally unique identifiers for:

- session;
- task;
- outcome contract and version;
- turn;
- activity;
- actor or principal;
- event;
- evidence;
- checkpoint;
- receipt;
- provider and model;
- canonical tool and provider-visible alias;
- MCP server and item;
- runtime generation;
- transaction or committed event batch.

Identifiers are stable strings in persisted protocols. Internal typed aliases are encouraged, but wire compatibility must not depend on Go type names.

Every event records enough correlation to answer:

- which journal kind, journal ID, and local sequence contains it;
- which session contains it when it is a session-journal event;
- which task and turn caused it;
- which activity it describes;
- which parent activity owns that activity;
- which earlier event caused this event;
- which actor or source produced it;
- which runtime generation was effective.

Fields not applicable to an event may be omitted. Journal kind and ID, event identity, local sequence, timestamp, kind, envelope version, and payload version are always required. Session identity is required for session-journal events and absent from workspace-control events.

## 7. Event Protocol

### 7.1 Envelope

The v2 envelope conceptually contains:

```json
{
  "schema_version": 2,
  "payload_version": 1,
  "journal_kind": "session",
  "journal_id": "ses_...",
  "event_id": "evt_...",
  "session_id": "ses_...",
  "seq": 42,
  "time": "2026-07-17T12:00:00Z",
  "kind": "activity.started",
  "task_id": "task_...",
  "turn_id": "turn_...",
  "activity_id": "act_...",
  "parent_activity_id": "act_...",
  "causation_event_id": "evt_...",
  "actor": {},
  "runtime_generation_id": "run_...",
  "transaction_id": "txn_...",
  "payload": {}
}
```

This is a semantic contract, not a requirement to flatten every property into one Go struct. Persisted field names and meanings must remain versioned.

### 7.2 Typed Payload Registry

Each known `kind + payload_version` pair defines:

- decoder;
- structural validator;
- semantic validator;
- canonical in-memory representation;
- projection handlers;
- redaction classification.

An unknown event kind with a structurally valid envelope is preserved and omitted from projections that do not understand it. A known event kind with an invalid payload is corruption and stops writable replay at the validated prefix.

### 7.3 Foundation Event Families

Foundation defines at least:

- session creation, fork, title, and lifecycle;
- task creation and status;
- outcome contract declaration, amendment, criterion assessment, and final assessment;
- turn accepted, state changes, terminal states;
- activity planned, authorized, started, progress, and terminal states;
- provider attempt and capability decision;
- execution plan and permission decision;
- evidence recorded and linked;
- checkpoint lifecycle;
- verification receipt lifecycle;
- context plan and usage records;
- runtime-generation activation;
- taskless control-operation lifecycle and authorization;
- recovery and migration diagnostics.

Runtime-generation activation, trust, credential state, MCP lifecycle, and taskless control-operation events belong to the workspace control journal. Session, task, turn, activity, permission, checkpoint, evidence-link, and outcome events belong to the session journal.

Streaming text and high-frequency progress may remain transient application events. Durable assistant messages, provider attempt terminals, action intents, decisions, evidence references, and terminal activity states are journal events.

## 8. Journal Contract

### 8.1 Required Operations

The workspace control journal and each session journal support:

- create journal and, for a session journal, create session;
- read session metadata without recovery mutation;
- read a bounded event range from a cursor;
- read the current local head;
- append one or more proposed events at an expected head;
- explicitly recover an incomplete or interrupted journal;
- explicitly migrate or mark format compatibility;
- create and inspect lineage references;
- rebuild indexes and projections.

### 8.2 Expected-Head Append

Every append includes the committed cursor expected by the caller. The committed cursor identifies the last committed local sequence and transaction. Physical lines from an incomplete transaction are not the committed head. If another writer changed the committed head, append fails with a typed conflict and writes nothing.

Serialization is per session, not per entire data root. Cross-process writers must be excluded through a documented lock or one-writer policy. In-process locks alone are insufficient. One process holds a cross-process turn lease for the complete active turn; a second process cannot start or resume a turn in that session until the durable active turn is terminal or explicitly recovered.

### 8.3 Committed Batches

Every v2 append request, including a single-event append, is framed as one or more event records sharing a transaction ID followed by one `transaction.committed` marker. The marker contains transaction ID, first and last event sequence, event count, and digest of canonical event records; it consumes the next ordinary local sequence. Projections expose the events only after a valid marker is durable.

A committed cursor is `{journal_kind, journal_id, commit_seq, transaction_id}`, where `commit_seq` is the marker sequence. Each legacy v1 line is an implicit one-event committed transaction represented as `{commit_seq: legacy_seq, transaction_id: "legacy:" + event_id}`. Mixed v1/v2 journals therefore use one cursor model.

A crash can leave a valid prefix of event records without a marker. Projections, expected-head checks, and caches use only the committed cursor. An incomplete transaction is quarantined before another append and never becomes visible through a later marker.

Append returns one of `committed`, `conflict`, `recovery_required`, or `commit_unknown`. `recovery_required` means an incomplete physical transaction must be quarantined before a new append. `commit_unknown` means durable commit may have succeeded but the caller could not confirm it; the caller must not retry blindly.

`LookupTransaction(transaction_id)` remains valid after later commits and returns `committed` plus resulting cursor, `not_committed` only after recovery durably quarantines it, or `unknown` when storage cannot determine the result. Metadata and transaction indexes are rebuildable from the journal. Metadata and head caches update only after journal commit.

The first v2 compatibility marker and its related initial events commit in one transaction.

Durability retains the v0.1 definition: files are synchronized and directory changes are synchronized where supported before an operation is reported durable.

### 8.4 Range Reads and Projection Snapshots

Full-session replay on every update is prohibited for the v0.2 canonical path. Consumers use event cursors, known journal heads, and versioned projection snapshots. Projection snapshots are disposable and rebuildable from the journal.

### 8.5 Recovery Separation

Reading does not silently truncate, append recovery events, or repair metadata. Recovery is an explicit operation with a durable result. A caller may request recovery during normal session open, but the distinction remains testable at the journal interface.

Recovery uses a crash-safe replacement protocol: preserve the invalid tail with digest, write and synchronize a temporary valid-prefix journal, synchronize required metadata, atomically activate the recovered journal, and synchronize the parent directory. Failure or process death at any step leaves either the original journal or a fully identifiable recovery candidate; it never silently discards both.

## 9. v0.1 Compatibility

### 9.1 Read Strategy

1. Existing v0.1 event lines are never rewritten in place.
2. The v0.2 reader accepts v1 and v2 envelopes.
3. v1 events are deterministically upcast in memory.
4. The first v2 append records the effective storage-format compatibility.
5. A session written by v0.2 is not assumed writable by v0.1; downgrade limits are documented.

### 9.2 Upcasting Rules

For v1 sessions:

- retain original event IDs, session ID, sequence, timestamp, kind, and raw payload;
- derive a turn at each `user.message` and close it at the next terminal turn event or before the next user message;
- scope call IDs to the derived turn, not the whole session;
- pair one request with ordered permission/start/result events; duplicate starts or terminals become migration diagnostics and the affected activity becomes uncertain;
- treat missing tool terminals as historical interruption and never synthesize success;
- accept every historical v1 payload shape enumerated by migration fixtures, including recovery-generated interruption payloads; malformed shapes make the validated prefix read-only;
- derive synthetic IDs as a documented hash of session ID, original event ID, derived turn ordinal, and activity ordinal;
- classify historical tool outputs and diffs as legacy evidence;
- set provider usage, cost, execution profile, verification status, and outcome-contract state to `unknown` unless explicitly represented;
- never classify an old successful tool result as a verification receipt;
- treat the session as a root with no parent lineage;
- preserve unrecognized payload fields for inspection.

Lossy upcasting records a migration diagnostic rather than inventing facts.

### 9.3 Compatibility Failure

An unsupported envelope version, unsupported payload version, unknown event without an explicitly understood safely-skippable projection marker, or invalid known event payload opens only the validated prefix in read-only mode. The original journal remains unchanged. A future salvage fork may use the validated prefix under the Security and Recovery specification.

## 10. Evidence and Recovery Material

### 10.1 Evidence Record

Evidence metadata includes:

- evidence ID and kind;
- content digest and algorithm;
- media type and byte size;
- producing activity and actor;
- subject reference, such as file, command, provider attempt, criterion, or remote resource;
- creation time;
- redaction and truncation metadata;
- immutable blob reference;
- legacy artifact alias where applicable.

### 10.2 Blob Storage

Blob identity is content-addressed. Blob paths are internal storage details and are not persisted as authorization identities. Session forks may reference parent evidence safely without copying blobs.

Evidence metadata and blob durability complete before `evidence.recorded` is committed. A missing or digest-mismatched blob invalidates verification that depends on it and produces a recovery diagnostic.

### 10.3 Confidential Recovery Material

Complete edit preimages are not ordinary evidence. They use an access-restricted confidential recovery store, are never model-visible or rendered, and are omitted from ordinary session and metric export. The store uses restrictive filesystem permissions and platform-backed encryption when available. If secure retention cannot be provided or registered secret bytes are detected, exact restore is disabled for that subject and only digest-based drift evidence remains.

### 10.4 Legacy Artifacts

Legacy artifacts are migrated lazily or through an explicit migration command:

1. validate path containment and regular-file safety;
2. compute content digest;
3. create evidence metadata;
4. preserve the legacy artifact ID as an alias;
5. avoid repeated hashing through durable migration metadata.

## 11. Activity Model

An activity contains:

- identity, task, turn, parent, actor, and source;
- a required durable purpose claim or system purpose for the operation;
- kind and current state;
- start and terminal timestamps;
- input and output evidence links;
- execution plan and authorization reference where consequential;
- requested and effective execution profile;
- error or uncertainty details;
- child activity summaries.

Foundation activity kinds include turn, context planning, provider attempt, action planning, authorization, tool execution, hook invocation, verification, checkpoint, restore, compaction, MCP lifecycle, and outcome assessment.

Lifecycle transitions follow the Capability Contract. Denied and cancelled-before-start activities never enter `started`. `interrupted_no_effect` is distinct from `uncertain`; the former requires proof that no effect began. Neither is a success state.

## 12. Turn Orchestration

### 12.1 Service Boundaries

The turn orchestrator coordinates interfaces equivalent to:

- task/outcome service;
- context planner;
- provider service;
- execution planner or tool catalog;
- authorization service and interactive approver;
- executor;
- evidence recorder;
- verification service;
- journal transaction service;
- application event publisher.

The orchestrator is the sole turn-journal committer and sole effect dispatcher. Bounded services return plans, policy results, evidence candidates, or verification candidates; they do not append turn events independently. Executors require an opaque committed-authorization token and cannot write the journal directly.

Taskless reload, MCP lifecycle, credential, and recovery work is represented by a durable `ControlOperation`. The application service serializes every consequential control operation through the same effect lane as turns. Generation preparation remains pure until an authorized control operation performs network or process activity.

### 12.2 State Machine

```text
accepted
  -> contract_drafting
  -> freezing_contract
  -> planning_context
  -> waiting_provider
  -> receiving_provider
  -> planning_action
  -> checkpointing
  -> awaiting_permission
  -> executing
  -> recording_evidence
  -> returning_result
  -> verifying
  -> completed | failed | interrupted
```

Contract drafting may use an authorized provider request and observation-only tools. Mutation-capable tools are absent until the contract is frozen. The provider-action-result loop may then repeat, but consequential operations remain sequential in model order. There is no parallel execution state in v0.2.

### 12.3 Durable Barriers

- goal and draft contract before contract-drafting provider egress;
- frozen contract before mutation-capable tools are advertised;
- canonical action plan, purpose, resources, and plan digest before checkpointing;
- checkpoint and confidential restore material before final authorization;
- final resource revalidation before authorization;
- authorization and atomic once-decision consumption before action start;
- action terminal and evidence before provider continuation;
- assistant terminal message before turn completion;
- criterion assessments before final task status and receipt.

## 13. Provider-Neutral Model

Foundation defines structured content blocks for at least:

- text;
- tool use;
- tool result;
- image or file reference;
- structured JSON;
- provider-visible reasoning summary when supported and allowed;
- refusal or safety result;
- usage and terminal metadata.

The model request includes a capability requirement set and a negotiated execution plan. The provider-neutral stream includes text/content deltas, completed content blocks, tool intents, usage updates, terminal reason, server request identity when available, and typed errors.

No native adapter is required in Gate 1, but fake adapters and contract fixtures must prove the normalized model supports the Extensibility spec.

## 14. Catalogs

### 14.1 Provider Catalog

The provider catalog resolves a configured provider/model identity to:

- adapter kind;
- model descriptor;
- known context window and maximum output;
- capability set in `supported`, `unsupported`, or `unknown` states with provenance;
- usage-reporting support;
- pricing metadata and provenance;
- credential binding reference;
- runtime generation.

### 14.2 Tool Catalog

The tool catalog supports built-in and future external tools. A canonical tool identity is independent of the provider-visible alias.

A tool descriptor includes:

- canonical identity and source;
- source revision and descriptor or schema digest;
- human display name and description;
- input and optional output schemas;
- effect and mutation classifications derived by Yordam's adapter; external annotations remain untrusted hints;
- possible execution loci;
- idempotency and retry classification;
- planning and execution interfaces.

Catalog alias collisions are rejected before provider exposure.

## 15. Structured Authorization

### 15.1 Request

An authorization request includes the fields required by the Capability Contract: actor, session or control operation, task/turn when present, activity, call or queue identity, source revision, action, structured resources, execution locus, requested/effective profile, effect class, reversibility, verification coverage, runtime generation, policy generation, and policy provenance.

### 15.2 Decision

A decision includes:

- `allow`, `deny`, or `ask`;
- structured constraints and canonical scope;
- `once` or `session` lifetime in v0.2;
- policy source and generation;
- human-readable reason;
- actor when resolved interactively;
- decision time and expiry conditions;
- execution-plan digest it authorizes;
- every request binding identity plus decision nonce.

An authorization cannot be reused if any binding changes. A once-decision is atomically consumed with the matching activity-start commit. A session grant remains bound to its session, canonical capability, source revision, descriptor digest, policy generation, and constraints.

### 15.3 Policy Precedence

Resolution uses a monotonic constraint lattice:

1. platform impossibility and hard deny are terminal;
2. user policy establishes the maximum capability set;
3. trusted project policy intersects and may only narrow that set;
4. ordinary deny is terminal;
5. a matching session grant may resolve only an effective `ask` inside all constraints;
6. an interactive response may resolve only the remaining `ask` and cannot override a deny.

Foundation maps `safe`, `ask`, and `auto` into this lattice for every consequential operation. Built-in behavior remains backward-compatible; unknown extension capabilities default to ask or deny rather than process-wide allow.

## 16. Application Protocol

### 16.1 Commands

Commands are versioned values with command ID, idempotency key, expected session/head when relevant, and typed payload. Duplicate command IDs produce the original result rather than repeating an effect. Foundation supports current v0.1 operations plus generic task start, control-operation start, cancel, permission resolution, snapshot request, and event subscription boundaries.

### 16.2 Snapshot

The canonical snapshot separates:

- durable workspace-control and session/task projections at one `ApplicationCursor` vector;
- ephemeral runtime status, including active streams and connection health.

It contains enough structure for later cockpit and headless adapters without exposing internal service pointers or Go errors. A single projection-locked operation returns a snapshot at `ApplicationCursor V = {workspace_control, selected_session?, stream_epoch, stream_seq}` and a subscription for events strictly after `V`, preventing snapshot/subscription gaps.

Durable catch-up reads each journal strictly after its vector component and merges events deterministically by timestamp then event ID. The selected session component changes explicitly on session switch. Live transient events use stream epoch/sequence; they are not resumable after a process epoch changes and clients receive a visible transient-gap marker before a fresh snapshot.

### 16.3 Events

Application events include:

- protocol version and stream event ID;
- session/task/turn/activity identity;
- time and kind;
- durable journal cursor when backed by a durable event;
- durable or transient classification;
- structured payload;
- redacted, stable error code and user-facing message.

The event subscription is bounded. Durable application events publish only after journal commit. Interactive reconnectable consumers may disconnect and resume from a cursor. A headless stdout consumer cannot reconnect; sustained backpressure cancels the turn and attempts an orderly terminal `RunReceipt` rather than silently dropping events.

## 17. System States and Errors

| State or Error | Expected Behavior |
|---|---|
| Expected-head conflict | Write nothing; caller reloads the current head and decides whether to retry planning |
| Incomplete event transaction | Ignore uncommitted events in projection; recovery terminalizes affected activity |
| Unknown or unsupported stateful event | Preserve for inspection; open validated prefix read-only unless explicitly safely skippable |
| Invalid known payload | Open validated prefix read-only |
| Missing evidence blob | Invalidate dependent verification and show recovery diagnostic |
| Projection-version mismatch | Rebuild projection from journal |
| Slow application-event consumer | Bound queue, disconnect consumer, permit cursor resume |
| Storage synchronization failure | Stop active turn before provider or effect continuation |
| v0.1 lossy upcast | Preserve raw payload and mark fields unknown |

## 18. Acceptance Criteria

- [ ] Given a valid v0.1 session fixture, when v0.2 loads it, then messages, tool lifecycle, decisions, file changes, and terminal turns project in original order without rewriting the source.
- [ ] Given v0.1 data without usage or verification, when upcast, then those fields remain `unknown` rather than inferred successful.
- [ ] Given two writers with the same expected head, when both append, then exactly one succeeds and the other receives a conflict with no partial write.
- [ ] Given a crash in a multi-event transaction, when recovered, then no uncommitted event affects canonical projections.
- [ ] Given an unknown authorization-critical event or unsupported payload version, when replayed, then the raw event is preserved, the session is inspectable, and no turn, grant, fork, or append can start past it.
- [ ] Given an invalid payload for a known kind, when replayed, then only the validated prefix is available and the source remains unchanged.
- [ ] Given evidence stored for an activity, when opened by ID, then its digest is revalidated and its provenance identifies the producing activity.
- [ ] Given two forks referencing identical evidence, when loaded, then both resolve the same immutable blob without copying session-local paths.
- [ ] Given a consequential built-in tool call, when execution begins, then frozen contract, canonical plan and purpose, checkpoint where required, final resource validation, authorization, and atomic once-decision consumption are already durable.
- [ ] Given a terminal tool result, when the provider receives it, then the result and evidence references are already durable.
- [ ] Given a scope or plan digest change after approval, when execution is attempted, then authorization is invalidated and no action starts.
- [ ] Given a provider with missing required capabilities, when negotiation runs, then it returns `capability_unavailable` without starting a provider request.
- [ ] Given TUI and fake headless adapters, when they consume the same snapshot and events, then durable task/activity state is semantically identical.
- [ ] Given a slow event subscriber, when its bounded queue fills, then the application remains bounded and the subscriber can recover from a cursor.
- [ ] Given two processes starting a turn in one session, when the cross-process lease is claimed, then only one turn starts and the other receives a durable conflict.
- [ ] Given a taskless local MCP start or remote probe, when it is requested, then it runs as an authorized serialized control operation and cannot overlap an active turn's consequential effect.
- [ ] Given a duplicate command ID or once-decision nonce, when replayed concurrently, then exactly one effect can start.
- [ ] Given all v0.1 acceptance tests, when run after Foundation, then they remain green or are replaced only by semantically equivalent v2 contract tests.

## 19. Gate Exit

Foundation exits only when:

- all acceptance criteria above pass;
- v0.1 session fixtures and acceptance behavior remain preserved;
- no later Trust Loop or Extensibility feature requires bypassing the new protocols;
- architecture review confirms the old `RunTurn` no longer owns context, provider translation, authorization, execution, evidence storage, and verification implementations directly;
- the Gate 1 acceptance evidence records one exact source commit.
