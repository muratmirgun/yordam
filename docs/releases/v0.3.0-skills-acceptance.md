# Yordam v0.3.0 Filesystem Skills Acceptance

## Metadata versus loaded body

Skills are discovered only at `~/.config/yordam/skills/<name>/SKILL.md` and at
`.yordam/skills/<name>/SKILL.md` under the canonical workspace. Discovery
accepts a bounded UTF-8 regular file with strict `name`/`description`
frontmatter; malformed, oversized, duplicate/ambiguous, traversal-looking, and
symlinked input is rejected with deterministic metadata diagnostics.

Global metadata is active user-managed input. Project metadata is `ask` by
default, and its durable allow/deny decision is bound to the canonical
workspace plus exact project catalog digest. `allow` activates and can shadow a
global name; `deny` does not. A changed digest is stale. System/provider context
gets metadata only until an explicit read-only `skill` tool call names an entry
from the frozen generation catalog. The tool is not a path reader. Reload
validates then activates a later generation; active turns and parent-to-child
handoffs retain the exact prior snapshot.

Skill bodies are untrusted instructions, never authorization. They cannot
bypass approval, mutate permission mode, execute hooks, read arbitrary files,
or disclose configured credentials. The acceptance fixture uses a hostile
trusted body and confirms the configured secret is absent from provider bodies,
durable events, artifacts/evidence, debug logs, public event/TUI projection,
and errors.

## Exact verification commands

The release gate is run from the task commit before recording its commit and
host evidence:

```sh
go test ./internal/skills ./internal/tools/skill ./internal/app ./internal/tui/... ./internal/acceptance -count=1
go test ./... -count=1
go test -race ./... -count=1
go vet ./...
git diff --check
```

The standalone deterministic acceptance entry point is:

```sh
go test ./internal/acceptance -run '^TestV030Skills$' -count=1
```
